# 第十二部　身份与权限 —— 用户账号

---

## 12.1　断点：账本在云端，可服务器怎么知道"你是你"？

第十一部结尾，那个一直被我们悄悄回避的问题，再也躲不过去了。

回头看后端代码，到处是 `请求.用户ID`：查账目要它、记账要它、删账要它。可这个"用户ID"，服务器**到底是怎么知道的**？

想清楚这个困境：

- 网页 `coinjar.example.com`，**全世界谁都能打开**；
- 账本却是**私密的**——你的账只能你看，你爱人的账只能他看；
- 服务器收到一个"查账目"的请求，**这个请求本身，并不会自带"我是谁"的可靠证明**。

这就好比：一家银行的大门敞开着，谁都能进来对柜员说"给我取一万块"。柜员凭什么知道这个人是谁？凭什么把钱给他、而不是给别人？凭什么相信他真是这个账户的主人？

> **断点：界面、数据、前后端都通了，但服务器还不知道"你是谁"。没有身份，"我的账本"就无从谈起。**

要解决它，需要三件环环相扣的事：

1. **注册**——先在服务器上，为你建立一个"身份"；
2. **登录**——你来的时候，证明"你就是那个身份的主人"；
3. **识别**——登录之后的每一个请求，服务器都能认出"这是你发的"。

这一部，就来把这三件事讲透。你会发现，它的内核，正是第六部"权限"思想，跨越网络的放大。

---

## 12.2　比喻：从大门钥匙，到带照片的工作证

先用一个生活场景，把整套身份机制的直觉建立起来——**进一栋写字楼上班**。

**第一天：注册。**
你入职，去前台登记。前台为你**建档**：记下你的姓名、工号，给你拍张照片存进系统，让你设一个**门禁密码**。从此，这栋楼的系统里，有了"你"这个人的档案。——这就是**注册**。

**每天早上：登录。**
你来上班，在门禁机上刷脸或输密码。系统核对："照片对得上 / 密码对得上 → 确认是你本人 → 开门。"——这就是**登录**，一次"证明你是你"的核对。

**进门之后：令牌。**
进门后，前台给你一张**当天的访客贴纸 / 工作证**，贴在胸口。之后你在楼里走动——进电梯、进茶水间、刷会议室——**保安只看你胸口的工作证，不再要求你每次都重新刷脸输密码。** 工作证就证明了"这人今早已经验过身份了"。——这就是**令牌**（token）。

**每个区域：权限。**
但工作证不是万能的。你的证能进 3 楼研发区，但进不了财务室、进不了机房——**不同的证，开不同的门。**——这就是**权限**。

把这套搬到 CoinJar：

> - **注册** = 在服务器上为你建档（用户名 + 密码）；
> - **登录** = 你用密码证明"你是你"，服务器核对通过；
> - **令牌** = 登录后服务器发给你的一张"电子工作证"，之后每个请求带着它，就不用反复输密码；
> - **权限** = 这张证能访问"你的"账本，但访问不了别人的。

这五个词——注册、登录、令牌、权限，外加一个"密码怎么存"——就是这一部的全部。我们一个个来。

## 12.3　注册：在服务器上为你建立一份"身份"

**注册**（sign up / register），就是在服务器的数据库里，为你**新建一条"用户记录"**。

```python
@服务器.路由("POST /注册")
函数 注册(请求):
    用户名 = 请求.body.用户名      # 比如 "小明"
    密码 = 请求.body.密码          # 比如 "mypassword123"
    
    # 1. 检查用户名是否已被占用
    if 数据库.查询("SELECT * FROM 用户表 WHERE 用户名=?", [用户名]):
        返回响应("用户名已存在", 状态码=409)
    
    # 2. 把新用户存进数据库（密码要先处理，见下一节！）
    数据库.执行(
        "INSERT INTO 用户表 (用户名, 密码) VALUES (?, ?)",
        [用户名, 处理后的密码]
    )
    
    返回响应("注册成功", 状态码=201)
```

注册做的事，本质上就是第九部的"存一条数据"——只不过这次存的不是账目，而是**一个用户**。从此，数据库的"用户表"里，多了"你"这个人。每一笔账目，都会关联到一个用户ID，这样服务器才能区分"哪些账是你的"。

```
用户表                          账目表
┌────┬────────┬────────┐       ┌────┬────────┬──────┬──────┐
│ID  │ 用户名  │ 密码    │       │ID  │用户ID  │ 金额  │ 类目 │
├────┼────────┼────────┤       ├────┼────────┼──────┼──────┤
│ 1  │ 小明    │ ****   │       │ 1  │  1     │ 18   │ 午饭 │ ← 小明的
│ 2  │ 小红    │ ****   │       │ 2  │  1     │ 30   │ 打车 │ ← 小明的
└────┴────────┴────────┘       │ 3  │  2     │ 50   │ 书   │ ← 小红的
                                └────┴────────┴──────┴──────┘
        每笔账目通过"用户ID"，关联到它的主人 ──┘
```

有了这个关联，第十一部那句 `SELECT * FROM 账目表 WHERE 用户ID=?` 才有意义——它能精确地只捞出"属于某个用户"的账。**身份系统，是"我的数据"这个概念的根基。**

但是，注册这一步藏着一个**极其重要、关乎安全**的细节——上面代码里那个 `处理后的密码`。为什么密码不能直接存？这是下一节的主题，也是整部书里安全意识最关键的一课。

## 12.4　密码为什么不能明文存：服务器也不该知道你的密码

新手最容易犯、后果最严重的错误，就是把用户密码**原样**存进数据库：

```python
# ❌ 绝对不能这样做！
数据库.执行("INSERT INTO 用户表 (用户名, 密码) VALUES (?, ?)", ["小明", "mypassword123"])
#                                                                          ↑ 密码原文裸存
```

为什么这是灾难？

> 想象数据库被黑客攻破了（这种事经常发生）。如果密码是**明文**存的，黑客一下子拿到了**所有用户的真实密码**。
> 更糟的是，很多人**所有网站用同一个密码**——于是黑客拿着从你这偷的密码，去登录用户的邮箱、网银、社交账号……灾难蔓延到整个互联网。
>
> 所以有一条铁律：**服务器，永远不应该知道用户的真实密码。**

这听起来很矛盾——**不知道密码，怎么验证登录？** 答案是一个精妙的技术，叫**哈希**（hash）。

**哈希**是一种特殊的"单向变换"：

- 它能把任意一段文字（比如密码 `mypassword123`），变成一串固定长度的、看起来乱七八糟的字符（比如 `a3f8e2...`）；
- **正着算很容易**：`mypassword123` → `a3f8e2...`，一算就出；
- **倒着推不回去**：拿到 `a3f8e2...`，**没有办法**反推出原来的 `mypassword123`。这就是"单向"。

> 哈希像**绞肉机**：把肉（密码）绞成肉馅（哈希值）很容易，但**没法把肉馅还原成一整块肉**。

于是，注册和登录变成了这样：

**注册时**：不存密码本身，只存密码的**哈希值**。
```python
密码哈希 = 哈希("mypassword123")   # 得到 "a3f8e2..."
数据库.存("小明", 密码哈希)         # 数据库里只有 a3f8e2...，没有真密码
```

**登录时**：把用户输入的密码也哈希一遍，比对两个哈希值。
```python
输入的哈希 = 哈希(用户这次输入的密码)
if 输入的哈希 == 数据库里存的哈希:
    # 两个哈希一样 → 说明输入的密码和当初注册的密码一样 → 验证通过！
```

妙在哪？

> - 服务器**全程不知道**你的真实密码，它只存了"绞碎的肉馅"（哈希值）；
> - 但它**依然能验证**你——因为同样的密码，绞出来的肉馅一定一样；
> - 哪怕数据库被偷，黑客拿到的只是一堆"肉馅"（哈希值），**还原不出真密码**。

（真实世界里还会加"盐"（salt）等手段进一步加固，细节你不必记。记住核心：**密码永远哈希后再存，服务器不该知道真密码。**）

这一节，是整部书"安全意识"的高光。它再次呼应第十一部那条铁律——**不要相信任何你控制不了的环节，连"存密码"这种事都要假设"数据库可能被偷"，提前做最坏的打算。** 这种"假设最坏情况"的防御性思维，是写云端程序的人必须刻进骨子里的。

## 12.5　登录：一次"证明你是你"的握手

注册建好了档，**登录**（log in）就是你每次回来时，证明"你是这个档案的主人"。

```python
@服务器.路由("POST /登录")
函数 登录(请求):
    用户名 = 请求.body.用户名
    密码 = 请求.body.密码
    
    # 1. 按用户名，从数据库找出这个用户
    用户 = 数据库.查询("SELECT * FROM 用户表 WHERE 用户名=?", [用户名])
    if not 用户:
        返回响应("用户名或密码错误", 状态码=401)   # 注意：不说"用户名不存在"（防止泄露信息）
    
    # 2. 把这次输入的密码哈希，和数据库存的哈希比对（12.4 节）
    if 哈希(密码) != 用户.密码哈希:
        返回响应("用户名或密码错误", 状态码=401)
    
    # 3. 验证通过！发给他一张"电子工作证"（令牌，下一节）
    令牌 = 生成令牌(用户.ID)
    返回响应({ "令牌": 令牌 }, 状态码=200)
```

登录的核心，就是 12.4 节那个哈希比对——**用户证明他知道密码，但服务器全程不接触真密码。** 验证通过后，关键的一步来了：服务器**发给他一张令牌**。

为什么需要令牌？这就要讲到网络一个让人头疼的特性了。

---

## 12.6　会话与令牌：登录之后，服务器怎么"记住"你

这里有个反直觉的事实，必须先讲清楚：

> **网络请求，天生是"健忘"的——每个请求之间，服务器默认互不相识。**

什么意思？你登录成功后，下一秒发一个"查账目"的请求——**服务器并不会自动记得"哦这是刚才登录的小明"。** 在服务器眼里，每个请求都是一个**陌生人**敲门，它默认谁也不认识。

这个特性叫**无状态**（stateless）。它就像那个写字楼的保安——**人来人往，他不可能记住每一张脸。** 你早上刷脸进了门，下午再路过，保安并不记得你今早验过身份了。

那怎么办？总不能每发一个请求，都重新输一遍用户名密码吧（那体验太糟了）。

解决办法，就是 12.2 节比喻里的**那张"工作证"——令牌（token）**：

```
1. 你登录成功
        ↓
2. 服务器发给你一张令牌（一串加密的、无法伪造的字符）
   令牌里"封装"着："这是用户ID=1的小明，他在今早10点验证过身份，有效期到晚上10点"
        ↓
3. 之后你发的【每一个】请求，都【带上】这张令牌
   GET /账目    （请求头里夹带：令牌 = "eyJhbGc..."）
        ↓
4. 服务器收到请求，先检查令牌：
   - 令牌是真的吗？（没被伪造、没过期）
   - 是真的 → 从令牌里读出"这是用户ID=1" → 哦，是小明！→ 返回小明的账
        ↓
5. 全程，你不用再输一次密码
```

这就解答了第十一部那个悬念——`请求.用户ID` 是哪来的：

> **它是从令牌里读出来的！**
> 你登录后，每个请求都带着令牌；服务器验证令牌，从中解出"你是谁"（用户ID），于是 `请求.用户ID` 就有了值。

令牌机制建立的这种"**登录一次，之后一段时间内都认得你**"的状态，叫一次**会话**（session）。它在"健忘的网络"之上，模拟出了"记得住你"的连续体验。

请你再次认出这个熟悉的模式：

> 第七部说，网络底层是不可靠的，但协议（TCP）通过"确认、重发"等机制，在不可靠之上**模拟出可靠**。
> 这里，网络是"健忘"（无状态）的，但令牌通过"每次带证"的机制，在健忘之上**模拟出"记得住"**。
>
> **在一个缺乏某种特性的底层之上，用巧妙的约定，模拟出那个特性——这是网络工程反复出现的智慧。**

## 12.7　读取"我的"数据：身份如何决定你能看到哪些账

身份接通后，第十一部那句反复出现的代码，终于完整闭环了。我们把"令牌→身份→数据"这条链补全：

```python
# 一个"检查令牌"的关卡，所有需要登录的请求都先过这道关
函数 检查身份(请求):
    令牌 = 请求.头部.令牌
    if not 令牌 or not 验证令牌(令牌):
        返回响应("请先登录", 状态码=401)   # 没令牌/令牌无效 → 挡在门外
    return 从令牌解出(令牌).用户ID          # 令牌有效 → 解出"你是谁"

@服务器.路由("GET /账目")
函数 查账目(请求):
    用户ID = 检查身份(请求)                  # ① 先确认你是谁
    # ② 只查"属于你的"账
    账目 = 数据库.查询("SELECT * FROM 账目表 WHERE 用户ID=?", [用户ID])
    返回响应(账目, 状态码=200)
```

整条链清清楚楚：

```
你登录 → 拿到令牌 → 请求带着令牌 → 服务器验令牌、解出用户ID
                                            ↓
                         数据库只捞"WHERE 用户ID=你" 的账
                                            ↓
                              你只看到"你的"账，别人的看不到
```

**这就是"我的账本"得以成立的全部机制。** 服务器不是凭感觉、凭信任，而是凭令牌里那个无法伪造的用户ID，精确地决定"该把谁的数据交给谁"。身份系统，是隐私和数据隔离的技术基石。

## 12.8　权限：能看 vs 能改——共记账本里谁能做什么

身份解决了"你是谁"，但还有一层——**"你能做什么"**。这就是**权限**（authorization）。

注意区分这两个词，它们常被搞混：

> - **认证**（authentication）：**你是谁**？（登录、令牌解决的）——查身份证。
> - **授权 / 权限**（authorization）：**你能干什么**？——你的身份证能让你进哪些门。
>
> 先认证（确认是你），再授权（看你能干啥）。先查证，再看权。

权限在 CoinJar 的"**和家人共记账本**"场景里变得很具体。假设你创建了一个"家庭账本"，邀请爱人加入。这时就有了不同角色：

- **账本拥有者**（你）：能记账、能删账、能**邀请/移除成员**、能**解散账本**；
- **普通成员**（你爱人）：能记账、能看账，但**不能解散账本**、不能踢人；
- **只读访客**（比如你想给父母看看）：**只能看，不能记、不能删**。

服务器在每个操作前，不仅要查"你是谁"，还要查"你有没有权限做这件事"：

```python
@服务器.路由("DELETE /账本/{账本ID}")
函数 解散账本(请求, 账本ID):
    用户ID = 检查身份(请求)                    # ① 认证：你是谁
    
    成员 = 数据库.查询("SELECT 角色 FROM 账本成员 WHERE 账本ID=? AND 用户ID=?",
                       [账本ID, 用户ID])
    if 成员.角色 != "拥有者":                   # ② 授权：你够格吗
        返回响应("只有账本拥有者能解散账本", 状态码=403)  # 403 = 没权限
    
    数据库.执行("DELETE FROM 账本 WHERE ID=?", [账本ID])
    返回响应("已解散", 状态码=200)
```

请你认出这位老朋友——**这正是第六部"权限"思想的放大。**

> 第六部：**操作系统**是关卡，审核每个应用的请求——"你有权限读这个文件吗？没有就驳回（拒绝）。"
> 第十二部：**服务器**是关卡，审核每个用户的请求——"你有权限解散这个账本吗？没有就驳回（403）。"
>
> | | 第六部 | 第十二部 |
> |---|---|---|
> | 谁来审核 | 操作系统 | 服务器 |
> | 审核谁 | 应用程序 | 用户 |
> | 凭什么审 | 进程的权限 | 用户的角色 |
> | 没权限时 | 拒绝系统调用 | 返回 403 |
>
> **同一种"在边界上设关卡、按身份决定能不能放行"的思想，从"操作系统管应用"，放大到了"服务器管用户"。**

至此，过渡章对照表里那条"第六部权限 → 第十二部权限"，也兑现了。

## 12.9　回到 CoinJar：让它支持注册、登录、和家人共享账本

把这一部学的全部装到 CoinJar 上，它终于成为一个**有用户、有隐私、能共享**的真正的多用户应用。

完整的用户旅程：

```
【注册】
小明打开 coinjar.example.com，点"注册"
→ 填用户名"小明"、密码
→ 前端 POST /注册
→ 服务器把密码【哈希】后存进数据库，建好小明的档案（12.3, 12.4）

【登录】
小明输入用户名密码，点"登录"
→ POST /登录
→ 服务器哈希比对，通过！发给小明一张【令牌】（12.5, 12.6）
→ 前端把令牌存起来

【使用】
小明记一笔"午饭18"
→ POST /账目，请求里【带着令牌】
→ 服务器验令牌、解出"用户ID=小明"，把账存进数据库、关联到小明（12.7）

小明查账
→ GET /账目（带令牌）
→ 服务器只返回"WHERE 用户ID=小明"的账——别人的账他看不到（12.7）

【共享】
小明创建"家庭账本"，邀请小红加入（小红是"成员"，小明是"拥有者"）
→ 两人都能往这个账本记账、都能看到对方记的（共享数据）
→ 但只有小明能解散账本、能踢人（权限区分）（12.8）
→ 小明想给爸妈"只读"看一眼，给他们"访客"角色——只能看不能改（12.8）
```

**CoinJar 现在是一个完整的多用户云端应用了**：每个人有自己的身份，每个人的账本相互隔离、安全私密，还能按权限和家人共享。过渡章最初那个"没法和家人共记一个账本"的痛点，到这里，被彻底、优雅地解决了。

回望一下，从过渡章到这里，CoinJar 长大了多少：

```
过渡章：困在单机里，账同步不了、没法共享
  ↓ 第七~八部：接入网络，拆成客户端+服务器
  ↓ 第九部：数据永久存进云端数据库
  ↓ 第十部：能用浏览器打开，不用装 App
  ↓ 第十一部：前后端分工，多设备共用一个后端
  ↓ 第十二部：有了身份、隐私、和家人共享
现在：一个真正的、多用户的、安全的现代 Web 应用
```

## 12.10　本章小结与断点预告

**这一章，我们给 CoinJar 接上了"身份"这条至关重要的连接：**

- 网页人人能开，但账本是私密的——服务器必须先知道"你是谁"，才有"我的账本"。
- **注册**：在数据库里为你建一份用户档案（第九部"存数据"的应用）。
- **密码必须哈希后存**：服务器永远不该知道真密码——用单向的哈希，做到"能验证、不知道、偷不走"。这是全书安全意识的高光，延续第十一部"不轻信、假设最坏"的防御思维。
- **登录**：用哈希比对证明"你是你"，通过后发给你一张**令牌**。
- **令牌 / 会话**：网络天生"健忘"（无状态），令牌让每个请求"带证上门"，在健忘之上模拟出"记得住你"——呼应第七部"在不可靠之上模拟可靠"的智慧。`请求.用户ID` 正是从令牌解出来的。
- **认证 vs 授权**：先确认"你是谁"，再决定"你能干什么"。
- **权限**：共享账本里区分拥有者/成员/访客——这是第六部"操作系统按权限放行"思想的放大：服务器在边界上按用户角色设关卡。
- CoinJar 成为完整的多用户应用：有身份、有隐私、能和家人安全共享。

**但是，最后一个断点，把 CoinJar 推向了与外部世界最深的一次连接。**

CoinJar 现在能记账、能算账、能多人共享。可记账记到最后，总有一笔账，你不只是想"记下来"，而是想"**真的把它付掉**"——比如账单里那笔"该还朋友的 200 块"，你希望在 CoinJar 里点一下，钱就真的转过去了。

> 可是——**CoinJar 自己，碰不到你的钱。**
> 它不是银行，没有你的存款；它也绝不该、绝不能直接去操作你的银行账户（想想这有多危险）。
> 一个记账小应用，凭什么能让真金白银从你的账户流出去？
>
> **断点：CoinJar 想完成一次真实的付款，但它根本够不到"钱"所在的地方——银行。**

要跨越这道鸿沟，CoinJar 必须学会和一类全新的伙伴打交道——**专业的第三方服务（支付平台）**。这也是你最初提的最后一个需求。

> **下一站，第十三部：应用与外部世界。**
> 我们将看到，CoinJar 是怎么把"付款"这件又专业又危险的事，安全地托付给支付平台，让钱真正流动起来的。你会发现，这是全书所有连接思想的一次大汇合——请求、回调、令牌、安全、边界，悉数登场。
