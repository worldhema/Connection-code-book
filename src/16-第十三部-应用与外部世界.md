# 第十三部　应用与外部世界 —— 接入支付

---

## 13.1　断点：CoinJar 想帮你直接付一笔钱，可它碰不到你的银行

第十二部结尾，CoinJar 已经是个完整的多用户应用了。但它的所有本事，都还停留在"**记录**"——记下你花了多少、欠了多少。

可记账的终点，常常是**付钱**。你的账单里有一笔"该还朋友的 200 块"，你最自然的愿望是：在 CoinJar 里点一下，这 200 块就**真的**转给朋友了，然后账目自动标记为"已付清"。

听起来理所当然。可一旦深想，你会发现一道几乎不可逾越的鸿沟：

> **CoinJar 自己，根本碰不到"钱"。**
> - 它不是银行，你的存款不在它手里；
> - 你的银行账户、密码、余额，它一概不知，也**绝对不该知道**；
> - 就算它知道，它也**绝对不能、绝对不敢**直接去划走你银行里的钱——想想这有多危险：一个记账小程序，能直接动你的银行存款？那它一旦被黑，或者代码写错，你的钱分分钟蒸发。

这道鸿沟，比之前任何一道都深。之前 CoinJar 够不到的，是"另一台机器""一个数据库"——而现在它够不到的，是**真金白银所在的金融系统**，一个戒备森严、责任重大、绝不容许出错的世界。

> **断点：CoinJar 想完成一次真实付款，但"钱"在银行，而它既够不到、也不被允许去碰。**

它该怎么办？答案是——**它不该自己碰钱，而应该把这件又专业又危险的事，托付给专门干这个的人。** 这就是这一部的主角：**第三方服务**。

## 13.2　比喻：你不会自己跑去银行金库，而是刷一下卡

想象你在一家商店买东西，要付 200 块。

**荒唐的做法**：商店对你说"请你自己跑去银行金库，搬 200 块现金过来给我。" ——这既危险（你得带着金库钥匙到处跑）、又愚蠢（每家店都得有套搬钱的本事）。

**现实的做法**：你掏出一张**银行卡**，在商店的 **POS 机**上刷一下，输个密码，"嘀"一声，付款成功。

请你仔细看这个再普通不过的动作里，藏着多精妙的分工：

- **商店**：它**全程没碰到你的钱**，也不知道你卡里有多少余额、密码是什么。它只是发起了一个"请收我顾客 200 块"的请求，然后等一个"收到了"的回执。
- **银行 / 支付网络**：真正"动钱"的，是它们——它们核对你的密码、检查余额、把钱从你账户划到商店账户。这些又专业又敏感的事，**只在它们戒备森严的系统里完成**。
- **POS 机 / 银行卡**：是商店和银行之间那个**标准化的中间环节**，让任何一家小商店，都能安全地接入庞大的银行系统，而不必自己懂金融。

把这套搬到 CoinJar：

> - **CoinJar** = 商店：它发起付款请求，但**绝不碰钱、不碰你的银行密码**；
> - **支付平台**（微信支付、支付宝、Stripe……）= POS 机 + 银行网络：它专门、专业地处理"动钱"这件危险事；
> - 你的钱，**只在支付平台和银行的系统里流动**，从头到尾不经过 CoinJar 的手。

这就是这一部的核心思想：

> **专业又危险的事，不要自己干，交给专门的人。**
> CoinJar 不学银行的本事，它只学会"如何安全地请支付平台帮忙"。

## 13.3　第三方服务：把"专业又危险的事"，交给专门的人

我们把这个思想正式化。

**第三方服务**（third-party service），就是由**专门的公司**提供的、解决某一类专业问题的网络服务。你的应用通过它的 API（第八部），把某件自己干不了或不该干的事，**外包**出去。

支付，是最典型的第三方服务，但远不止它。你天天用的 App 背后，到处是第三方服务：

- 要发短信验证码？接入**短信服务**（专门的公司有和运营商的通道）；
- 要显示地图、导航？接入**地图服务**；
- 要存海量图片视频？接入**云存储服务**；
- 要收款付款？接入**支付服务**。

为什么要外包，而不自己干？因为这些事，往往有三个共同点：

1. **极其专业**：支付要懂金融、懂风控、对接几十家银行；短信要和运营商谈通道。从头自建，要耗费巨大的人力和时间。
2. **极其危险/敏感**：钱、用户隐私——一旦出错，是灾难级的。专业公司有成熟的安全体系和资质牌照（比如支付牌照），你自己很难达到。
3. **有现成的、可靠的服务**：既然有专业公司把这件事做到了极致，你只需"接入"，何必重造轮子？

这正是全书一个核心思想的又一次、也是最高一次的升华：

> 第二部：**接口与实现分离**——你用一个模块，不必知道它内部怎么实现。
> 第八部：**API**——你用一个服务器，不必知道它内部怎么干活。
> 第十三部：**第三方服务**——你用支付平台，**完全不必、也无权知道**它内部怎么和银行打交道、怎么动钱。
>
> 你只需面对它给的那套 API（承诺），把请求发过去、等结果回来。
> **它内部那个又专业又危险的世界，被一道 API，干干净净地隔在了外面。**

"隐藏复杂、只暴露简单接口"——这个从第一部"函数"就开始的思想，到这里，隔离的已经不是一段代码、一个程序，而是**整个金融系统的复杂与风险**。

## 13.4　支付的连接链：App → 服务器 → 支付平台 → 银行

现在看一次付款，到底有多少个环节在接力。这是全书最长的一条连接链，但你会发现每一环都是学过的东西。

```
用户（在 CoinJar 网页/App 上点"支付 200 元"）
   │
   ▼  ① 网络请求（第八、十一部）
CoinJar 后端服务器
   │   （它不碰钱，只是"发起一个支付订单"）
   ▼  ② 网络请求，调用支付平台的 API（第八部）
支付平台（微信支付/支付宝/Stripe）
   │   （专业处理：核对、风控、对接银行）
   ▼  ③ 在金融网络内部动钱（CoinJar 完全看不到这一层）
银行 / 金融网络
   │   （真正把 200 块从用户账户划走）
   ▼
   钱，付出去了
```

请你特别注意 CoinJar 在这条链里的位置和姿态：

> **CoinJar 后端，对支付平台来说，是一个"客户端"**（第八部的角色，又出现了）。
> 它向支付平台**发起请求**："请帮我向用户收 200 块。"
> 然后它**等响应**，支付平台处理完告诉它结果。
>
> 而支付平台之后做的一切——怎么验证用户、怎么对接哪家银行、钱怎么在金融系统里流转——**CoinJar 一无所知，也无需知道。** 那是 API 背后的"实现"，被隔离了。

你看，第八部"客户端—服务器—请求—响应"那套骨架，在这里**原封不动**地复用了。只不过这次的"服务器"，是一个专业的支付平台；这次的"请求"，关乎真金白银。**同一种连接思想，又一次在更高、更关键的尺度上重演。**

## 13.5　为什么钱的事要绕这么多手：信任、安全与责任

你可能会问：绕这么多环节（App→服务器→支付平台→银行），不嫌麻烦吗？为什么不能 CoinJar 直接和银行对接，少几道手续？

恰恰相反，**这些"麻烦"的环节，每一道都在解决一个要命的问题。** 我们逐一看：

**① 为什么付款要经过 CoinJar 的"后端"，而不是网页前端直接发起？**

回想第十一部那条铁律：**永远不要相信前端。** 前端跑在用户浏览器里，能被篡改。如果让网页前端直接告诉支付平台"收 200 块"，黑客就能把它改成"收 0.01 块"或别的花样。所以**发起支付这种关键操作，必须由可信的后端来做**——后端是你能控制的、安全的一侧。（第六、十一、十二部那条"在可信的边界内做关键决策"的线，又一次延续。）

**② 为什么要经过"支付平台"，而不是 CoinJar 直接连银行？**

- **专业与资质**：直接对接银行需要金融牌照、需要满足极严苛的安全审计，绝大多数应用没这个资格和能力。支付平台有牌照、有和几十家银行打通的通道，它把这一切复杂性"打包"成一套 API。
- **安全**：用户的银行卡号、密码这些最敏感的信息，**只交给有资质的支付平台**，绝不流经 CoinJar。这样即使 CoinJar 被黑，黑客也拿不到任何人的银行信息——因为 CoinJar 压根就没存过、没碰过。
- **责任**：钱出了问题（重复扣款、扣了没到账），有专业的支付平台来对账、追溯、担责。

**③ 为什么用户的银行密码，CoinJar 永远不该看到？**

这和第十二部"密码哈希"是同一种思想的延续，甚至更严格：

> 第十二部：连用户登录 CoinJar 的密码，CoinJar 都不该知道（要哈希）。
> 第十三部：用户的**银行**密码，CoinJar **更加**不该、不能、不准接触——它要在支付平台自己的安全页面里输入，CoinJar 全程看不到。
>
> **越敏感的信息，越要隔离在专业、可信的一方手里。你的应用知道得越少，反而越安全。**

所以那些"绕来绕去"的环节，不是冗余，而是**用层层分工，把信任、安全、责任，分配给了最有能力承担它的一方。** 这是成熟系统的标志——**没有任何一方需要"无所不能"，每一方只做自己最该做、最能做好的那一段。**

## 13.6　回调与对账：钱付完了，谁来通知你的应用

这里有一个网络支付特有的、极其重要的细节，它把全书的一个老朋友推向了高潮——**回调**。

问题是这样的：CoinJar 发起支付后，用户被带到支付平台去付款（输密码、确认）。这个过程**可能要花几秒、十几秒，甚至更久**（用户可能犹豫、可能切去别的页面）。CoinJar 的服务器**不可能傻等着**——它得去处理别的请求。

那么，**用户最终付成功了没有，CoinJar 怎么知道？**

答案是：**不是 CoinJar 去反复追问，而是支付平台付完后，"反过来"主动通知 CoinJar。** 这个"反过来通知"，就是**回调**（callback）——也叫"支付通知 / webhook"。

```
1. CoinJar 后端 → 支付平台：发起支付，并告诉它：
   "付款有结果了，请通知我这个地址：https://coinjar.example.com/支付回调"
        │
        ▼
2. 用户在支付平台的页面上，输密码、确认付款（CoinJar 此时在干别的事）
        │
        ▼
3. 支付平台处理完（钱划走了），【反过来】向 CoinJar 那个地址发一个请求：
   POST https://coinjar.example.com/支付回调
   内容："订单 #123 已支付成功，金额 200 元"
        │
        ▼
4. CoinJar 后端收到这个回调，才知道："哦，付成功了！"
   → 把对应账目标记为"已付清"
   → （可能再通知前端刷新界面）
```

请你认出这个贯穿全书的老朋友，并看清它这一路是怎么长大的：

> - **第五部**：界面把一个函数交给逻辑层——"数据变了就喊我"（同一程序内的回调）。
> - **第十一部**：前端把一个函数交给"网络请求"——"服务器回话了就喊我"（跨网络的回调）。
> - **第十三部**：CoinJar 把一个**网址**交给支付平台——"付款有结果了就喊我"（跨公司、跨系统的回调）。
>
> 这正是过渡章对照表那条线的终点：**回调（第五部）→ 支付回调（第十三部）。**
> 从"你变了喊我"，到"服务器回话喊我"，到"另一家公司办完事喊我"——
> **同一种"我不盯着你，你办完了主动喊我"的思想，一路放大到了公司与公司之间。**

这里还有一个关乎钱、绝不能马虎的纪律——**对账**：

> 回调可能丢失（网络不可靠，第七部！万一那个"已支付"的通知没送达 CoinJar 怎么办？）。
> 所以正经的支付系统，除了被动等回调，还会**主动定期去支付平台查询订单状态**（"我那笔订单 #123 到底成没成？"），两边核对，确保账目和真实付款**一分不差**。
>
> 这是第七部"网络不可靠"在"钱"这件事上的终极体现：**关乎钱，永远不能只信一条消息，必须双重确认。**

## 13.7　密钥与安全：和外部服务说话，怎么证明"请求是我发的"

最后一块拼图，关乎安全。

CoinJar 向支付平台发请求"帮我收用户 200 块"。支付平台凭什么相信，这个请求**真的是 CoinJar 发的**，而不是某个骗子冒充 CoinJar 发来的（想骗支付平台给自己收钱）？

反过来，13.6 节那个"支付成功"的回调，CoinJar 又凭什么相信，它**真的来自支付平台**，而不是骗子伪造的（伪造一个"已支付"，骗 CoinJar 把没付钱的账标成已付清）？

双方都需要一种办法，来**证明"我是我"**。这靠的是**密钥**（secret key）。

> 当 CoinJar 在支付平台注册成为商户时，支付平台会发给它一把**密钥**——一串只有 CoinJar 和支付平台两方知道的、绝密的字符。
>
> - CoinJar 发请求时，用这把密钥给请求"**签名**"（生成一个无法伪造的标记）；
> - 支付平台收到，用同一把密钥验证签名——对得上，才确认"这真是 CoinJar 发的"；
> - 回调也一样：支付平台用密钥签名，CoinJar 验证，确认"这真是支付平台发的"。

你又一次见到了熟悉的影子——这和第十二部的"令牌"是同一种思想：

> - 第十二部 **令牌**：证明"这个请求来自已登录的某个**用户**"。
> - 第十三部 **密钥签名**：证明"这个请求来自可信的某个**应用/服务**"。
>
> 都是在不可信的网络上，用一个"无法伪造的凭证"，回答那个根本问题：**"你怎么证明你是你？"**

而密钥的保管，又呼应了密码哈希的那条铁律：

> **密钥是绝密，绝对不能写进网页前端**（前端能被用户看到，密钥一泄露，骗子就能冒充你）。
> 它只能藏在**后端服务器**这个可信的地方。
> ——再一次："越敏感的东西，越要藏在你能控制的、可信的那一侧。"

这条从第六部（权限）、第十一部（不信前端）、第十二部（密码哈希）一路贯穿下来的**安全主线**，到这里画上了一个完整的句号：**信任要建立在可验证的凭证上，秘密要保管在可信的边界内。**

## 13.8　回到 CoinJar：接入一个支付平台，完成一次真实付款

把这一部学的全部缝起来，让 CoinJar 完成它一生中最重的一次连接——一笔真实的付款。

```python
# CoinJar 后端：接入支付平台

支付密钥 = 读取环境变量("支付平台密钥")   # 绝密！只在后端，绝不进前端（13.7）

# —— ① 用户点"支付"，前端请求后端发起支付 ——
@服务器.路由("POST /发起支付")
函数 发起支付(请求):
    用户ID = 检查身份(请求)                    # 第十二部：先确认你是谁
    账目ID = 请求.body.账目ID
    金额 = 数据库.查询("SELECT 金额 FROM 账目表 WHERE ID=? AND 用户ID=?",
                      [账目ID, 用户ID]).金额    # 金额从【后端数据库】取，不信前端传的（第十一部）
    
    # 后端调用支付平台的 API（第八部：CoinJar 此刻是支付平台的"客户端"）
    支付结果 = 调用支付平台API(
        方法="创建订单",
        金额=金额,
        订单号="订单#" + 生成订单号(),
        回调地址="https://coinjar.example.com/支付回调",   # 告诉平台：办完喊我（13.6）
        签名=用密钥签名(...)                                # 证明"这请求是 CoinJar 发的"（13.7）
    )
    
    # 把支付平台返回的"付款页面链接"给前端，让用户去那里付款
    返回响应({ "付款链接": 支付结果.付款页面 }, 状态码=200)
    # ↑ 用户将在【支付平台自己的安全页面】输入银行密码，CoinJar 全程看不到（13.5）

# —— ② 支付平台付款完成后，回调通知 CoinJar ——
@服务器.路由("POST /支付回调")
函数 支付回调(请求):
    # 先验证：这个回调真的来自支付平台吗？（13.7）
    if not 验证签名(请求, 支付密钥):
        返回响应("签名无效，拒绝", 状态码=403)   # 防伪造的"已支付"
    
    订单号 = 请求.body.订单号
    if 请求.body.状态 == "支付成功":
        把对应账目标记为已付清(订单号)            # 更新数据库
    
    返回响应("收到", 状态码=200)

# —— ③ 兜底：定期主动对账，防止回调丢失（13.6）——
定时任务 每隔几分钟:
    对于 每个"发起了但还没确认"的订单:
        真实状态 = 主动查询支付平台(订单号)        # 不只信回调，主动再确认一遍
        if 真实状态 == "支付成功":
            把对应账目标记为已付清(订单号)
```

一次完整的真实付款，串起了卷二（乃至全书）的几乎所有连接：

```
用户在 CoinJar 点"支付这笔 200 元"
  → 前端发请求给后端                                    （第十一部 事件→请求）
  → 后端验证身份、从数据库取真实金额                      （第十二部 身份 + 第十一部 不信前端）
  → 后端用密钥签名，调用支付平台 API                      （第八部 客户端→服务器 + 13.7 密钥）
  → 支付平台返回付款链接，用户跳转过去                     
  → 用户在【支付平台】输银行密码付款（CoinJar 看不到）      （13.5 隔离敏感信息）
  → 钱在【银行/金融网络】真正划转                          （13.4 CoinJar 够不到的那一层）
  → 支付平台回调 CoinJar："成功了"                        （13.6 回调，第五部思想的终点）
  → CoinJar 验签、标记账目"已付清"                        （13.7 验证 + 第九部 写数据库）
  → （兜底）定时主动对账，防回调丢失                       （13.6 + 第七部 网络不可靠）
  → 前端刷新，用户看到"已付清"                            （第十一部 回调刷新界面）
```

**CoinJar 至此，连上了整个世界。** 它从序章那个"只会记一笔、一关就忘"的单机代码片段，一路长成了一个**能记账、能算账、能多人共享、能注册登录、还能完成真实付款**的完整现代应用。它的连接,从一台机器内部的函数调用,一路延伸到了银行的金融网络。

## 13.9　收束：CoinJar 已经连上了整个世界

写到这里，卷二的旅程，圆满了。

请你回望 CoinJar 这一路接起的所有连接，它们像一圈一圈不断扩大的涟漪：

```
卷一（单机篇）：一台机器内部
  函数 ↔ 函数 → 模块 ↔ 模块 → 文件 ↔ 文件 → 目录 ↔ 目录
  → 代码 ↔ 界面 → 应用 ↔ 系统

卷二（网络篇）：跨越机器、跨越世界
  机器 ↔ 机器 → 程序 ↔ 程序 → 数据 ↔ 云端 → 服务器 ↔ 浏览器
  → 网页 ↔ 界面 → 身份 ↔ 权限 → 应用 ↔ 外部世界（银行）
```

而你已经无数次地见证了那个最重要的事实——**这十三部，讲的从来不是十三种互不相干的知识，而是同一种"连接思想"，在不断放大的尺度上的重演：**

- "**调用**"，从函数之间，放大到系统调用、网络请求、调用支付平台；
- "**寻址**"（怎么找到对方），从函数名、文件路径，放大到 IP、端口、域名；
- "**接口/约定**"，从模块接口，放大到 API、网络协议、第三方服务；
- "**分层**"，从界面与逻辑，放大到前端与后端、应用与系统与数据库；
- "**回调**"，从界面刷新，放大到网络响应、支付通知；
- "**边界与安全**"，从操作系统权限，放大到不信前端、密码哈希、密钥签名。

序章那句话，此刻你应该有了切肤的理解：

> **节点是零件，连线才是机器。**
> 让 CoinJar 从一段代码长成一个连接世界的应用的，从来不是某一行厉害的代码，
> 而是这一层又一层、从小到大、彼此咬合的**连接**。

CoinJar 现在是一个连上了整个世界的应用。它能记录、能计算、能协作、能交易。

但它仍然只会**按指令办事**——你说"午饭18"，它记一笔；你点"支付"，它走流程。它不懂你说的话，不会主动帮你，更不会自己思考"这个月你是不是吃外卖花太多了"。

而我们正站在一个新时代的门口。当机器开始**听懂人话、能调用工具、能自主思考与协作**时，"连接"这件事，将迎来它有史以来最深刻的一次放大——**人与机器之间的连接，机器与机器之间的智能协作。**

那是卷三的故事。CoinJar 的旅程，还没有结束。
