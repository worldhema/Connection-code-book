# 第十部　服务器与浏览器 —— 网页是怎么来的

---

## 10.1　断点：不想装 App，能不能打开网址就用？

第九部结尾，CoinJar 已经是个像模像样的云端应用了：数据永久存在服务器、客户端能查能记。

但客户端是个 **App**——用户得先去应用商店**下载、安装、更新**，才能用。这道门槛挡住了很多人：

- 有人手机存储满了，不想再装一个 App；
- 有人只是想偶尔记一笔，专门装个 App 太重；
- 有人在公司电脑上，根本没权限装软件；
- 你想把账本分享给朋友看一眼，总不能让对方先装个 App 吧？

而你天天访问的淘宝、知乎、B站、维基百科……大多数都不用装 App：**打开浏览器，输入网址，回车，就能用。**

> **断点：能不能让 CoinJar 也这样——不装任何东西，打开浏览器、输入网址，就能记账？**

要做到这一点，服务器必须学会一件新本事：当有人用浏览器访问它时，**给浏览器送回一个"能看、能点、能用"的网页**。

这一部，我们就来看这个网页是怎么"来"的。

---

## 10.2　比喻：你点一份菜，后厨现做现端上桌

还记得第五部那个"前厅与后厨"的比喻吗？这一部，它要回来了——只是这次，前厅和后厨之间隔了一条街（网络）。

想象一家**外卖餐厅**：

- 你（**浏览器**）在家，想吃饭；
- 你打电话给餐厅（**服务器**）："我要一份宫保鸡丁套餐"（访问网址）；
- 餐厅后厨**现做**这份套餐，装进餐盒（**生成网页**）；
- 外卖小哥把餐盒**送到你家**（**网络传输**）；
- 你打开餐盒，摆上桌，开吃（**浏览器把网页画出来，你看到、能用**）。

关键点：

> **你（浏览器）自己不做菜，你只是"提出要求 + 接收成品 + 享用"。**
> **餐厅（服务器）做菜（生成网页），但它不亲自喂你吃——它把成品送过去，由你自己摆盘享用。**

把这套搬到 Web 世界：

> - **浏览器** = 你 + 你家的餐桌（提出请求、接收网页、把网页"画"出来给你看）；
> - **服务器** = 餐厅后厨（收到请求、生成网页、送回去）；
> - **网页** = 那份打包好的套餐（一份描述"界面长什么样"的文件）；
> - **网络** = 外卖小哥（负责把网页从服务器送到浏览器）。

这一部的核心问题就是：**这份"套餐"（网页）是什么、服务器怎么做、怎么送、浏览器怎么把它摆上桌。**

---

## 10.3　浏览器是什么：一个会"取网页、画网页"的通用程序

我们先认识"前厅"这一侧的主角——**浏览器**（browser）。Chrome、Safari、Edge、Firefox……都是浏览器。

浏览器到底是什么？它是一个**通用程序**，专门干两件事：

1. **取网页**：你输入网址，它向对应的服务器发请求，把网页"取"回来；
2. **画网页**：它读懂网页文件的内容，在屏幕上**画出**对应的界面——标题、按钮、输入框、图片……让你能看、能点。

请你品味"**通用**"这两个字的分量。这是浏览器最了不起的地方：

> 第五部，CoinJar 的桌面界面，是我们**专门为 CoinJar 写的**——换个应用，界面得重写。
>
> 但浏览器是**通用的**——同一个 Chrome，今天打开淘宝、明天打开知乎、后天打开 CoinJar，**它都能正确地画出来**。
>
> 为什么？因为所有网页都遵守**同一套约定**（同一种描述界面的"语言"，见 10.5 节）。浏览器只要懂这套约定，就能画出**任何**遵守约定的网页。

这又是"约定"的威力——和第七部的"协议"、第二部的"接口"一脉相承：

> **只要大家都遵守同一套约定（网页的语言），一个通用的程序（浏览器）就能服务无数不同的应用（网站）。**

这就是为什么你的手机里，不需要为每个网站装一个 App——一个浏览器，通吃所有遵守 Web 约定的网站。浏览器，是人类历史上最成功的"通用客户端"。

## 10.4　一次"打开网址"背后发生了什么

你在浏览器输入 `coinjar.example.com`，按下回车。短短一瞬间，背后发生了一长串我们已经学过的事。让我们慢镜头回放——你会发现，这一部之前学的所有东西，全用上了：

```
1. 你输入 coinjar.example.com，回车

2. 浏览器：这是个域名，得先翻成 IP（第八部 域名/DNS）
   → 问 DNS："coinjar.example.com 是哪个 IP？"
   → DNS 回答："203.0.113.45"

3. 浏览器：现在我知道服务器的门牌号了（IP），也知道找网页服务要走 443 端口（第八部 端口）
   → 向 203.0.113.45:443 发起一个请求（第八部 客户端→服务器）
   → 请求内容："GET /  请把首页网页给我"

4. 网络：请求拆成数据包，一跳接一跳送到服务器（第七部 数据包/路由）

5. 服务器：收到请求，触发"返回首页"的逻辑（第八部 服务器处理请求）
   → 生成网页内容（一份描述界面的文件，见 10.5）
   → 构造响应：{ 状态码 200, 内容: <网页文件> }

6. 网络：响应送回浏览器

7. 浏览器：收到网页文件
   → 读懂它（解析）
   → 在屏幕上**画出来**：标题、输入框、按钮、账目列表……
   → 你看到了 CoinJar 的网页，可以开始用了
```

**请你看清楚——这就是第八部的"请求与响应"，一字不差。**

> 第八部，客户端 App 向服务器请求**数据**，服务器响应**数据**。
> 第十部，浏览器向服务器请求**网页**，服务器响应**网页**。
>
> **同一套"请求—响应"骨架，只是这次响应的内容，从"一串数据"变成了"一整个界面"。**

浏览器，本质上就是第八部那个"客户端"——只不过它是一个**通用**的客户端，且它收到响应后会把内容**画成界面**。所以你完全可以说：**浏览器，就是一个会画界面的客户端。**

## 10.5　HTML / CSS / JS：网页的"骨架、皮肤、动作"

那份服务器送来、浏览器画出的"网页文件"，到底是什么？

它主要由三种东西组成，各管一摊，配合默契。我们用"造一个人"来比喻：

### HTML —— 骨架（内容与结构）

**HTML**（HyperText Markup Language，超文本标记语言）规定网页上**有什么、是什么**：这里有个标题、那里有个输入框、下面有个按钮、再下面有个列表……

它就像人的**骨架**——决定了"有哪些部位、怎么搭起来"。

```html
<h1>我的账本</h1>
<input placeholder="午饭 18">
<button>记一笔</button>
<ul>
  <li>午饭 ¥18.00</li>
  <li>咖啡 ¥25.00</li>
</ul>
```

光看这段，你大概都能猜出来：一个标题"我的账本"、一个输入框、一个按钮、一个两行的列表。HTML 就是这么直白地描述"网页上有什么"。

### CSS —— 皮肤（样式与外观）

**CSS**（Cascading Style Sheets，层叠样式表）规定网页**长什么样、好不好看**：标题用多大字号、按钮是什么颜色、整体怎么排版、间距多大……

它就像人的**皮肤、衣着、长相**——同样的骨架，配不同的 CSS，可以丑得像 1995 年的网页，也可以美得像今天的苹果官网。

```css
h1 { color: 深蓝; font-size: 24px; }
button { background: 橙色; border-radius: 8px; }
```

### JavaScript —— 动作（行为与交互）

**JavaScript**（简称 JS）规定网页**能做什么、怎么响应你**：点了按钮发生什么、输入时实时校验、动态更新列表……

它就像人的**肌肉和神经**——让原本静止的骨架"动"起来、能对你的操作做出反应。

```javascript
button.onclick = function() {
    // 点了"记一笔"按钮，发一个请求给服务器
    发请求("POST", "/账目", 输入框的内容)
}
```

请你注意最后这段 JS——它做的事，正是第五部的**事件处理**！"点击按钮 → 触发函数"。只不过这次，触发的函数里，干的是"向服务器发网络请求"。

> **三者合一**：
> - **HTML** 给骨架（有什么）
> - **CSS** 给皮肤（什么样）
> - **JS** 给动作（怎么动）
>
> 浏览器把这三样读懂、合成，就在你眼前画出了一个**能看、能点、能用**的网页。

这三种语言的具体语法，你**完全不必记**。你只需记住这个"骨架 / 皮肤 / 动作"的三分法——它会帮你看懂任何一个网页的构成。

## 10.6　服务器如何把网页"送"到浏览器

服务器怎么"送"网页？其实第八部你已经会了——网页就是一种特殊的"响应内容"。

```python
# CoinJar 服务器：返回网页

@服务器.路由("GET /")
函数 返回首页():
    网页内容 = """
    <h1>我的账本</h1>
    <input id="输入框" placeholder="午饭 18">
    <button onclick="记账()">记一笔</button>
    <ul id="账目列表"></ul>
    <style> button { background: 橙色; } </style>
    <script> ... 这里是 JS ... </script>
    """
    返回响应(网页内容, 状态码=200, 类型="text/html")
    #                                  ↑ 关键：告诉浏览器"这是个网页，请画出来"
```

和第九部"返回数据"的唯一区别，是那个**类型**标记：

- 返回数据时，类型是 `application/json`（告诉客户端"这是数据，自己处理"）；
- 返回网页时，类型是 `text/html`（告诉浏览器"这是网页，请画出来"）。

浏览器看到 `text/html`，就知道："哦，这是要我画的网页。" 于是它启动渲染引擎，把 HTML/CSS/JS 读懂、合成、画到屏幕上。

> 这又是"约定"的细节体现——响应里带一个"类型"标记，是服务器和浏览器之间的约定，让浏览器知道该拿这份内容怎么办。和第三部"文件扩展名（.py/.png）告诉系统这是什么文件"，是同一种思想：**用一个标记，声明内容的类型，好让接收方知道如何处理。**

## 10.7　静态与动态：现成的网页，与按你的数据现拼的网页

服务器送网页，有两种做法，区别很重要：

### 静态网页：现成的、人人一样

有些网页是**事先做好、固定不变**的——比如 CoinJar 的"关于我们"页、"使用帮助"页。每个访客看到的都一模一样。服务器把一个早就写好的网页文件,原封不动送出去就行。

> 像便利店货架上的**预包装食品**——做好了摆在那，谁来拿都是同一份。

### 动态网页：按你的数据，现场拼出来

但 CoinJar 的核心页面——"我的账本"——**每个人看到的内容都不一样！** 你看到的是你的账，你爱人看到的是他的账。这个网页**不可能事先做好**，因为服务器在做这个网页时，得先知道"现在是谁在看、他有哪些账"。

所以这种网页是**动态生成**的：

```python
@服务器.路由("GET /我的账本")
函数 返回账本页(请求):
    用户ID = 请求.用户ID
    
    # 1. 先从数据库查出"这个用户的账目"（第九部）
    账目列表 = 数据库.查询("SELECT * FROM 账目表 WHERE 用户ID=?", [用户ID])
    
    # 2. 把账目"拼"进网页的 HTML 里
    账目HTML = ""
    对于 每一笔账 在 账目列表:
        账目HTML += f"<li>{每一笔账.类目} ¥{每一笔账.金额}</li>"
    
    网页内容 = f"""
    <h1>我的账本</h1>
    <ul>{账目HTML}</ul>     ← 这里塞进了"这个用户的"账目
    """
    
    返回响应(网页内容, 状态码=200, 类型="text/html")
```

> 像餐厅的**现炒菜**——你点了才做，而且按你的口味（你的数据）现场定制。

**静态 vs 动态，本质区别**：

> - **静态**：网页内容固定，和"谁在看"无关——服务器拿现成的送出去。
> - **动态**：网页内容取决于"谁在看、他的数据是什么"——服务器先查数据库（第九部），再把数据"拼"进网页，现场生成。

CoinJar 这种应用，几乎全是动态网页——因为它的核心价值，就是"展示**你的**数据"。而动态生成的前提，是第九部那个数据库——没有数据库存着每个人的账，服务器就拼不出"你的"账本页。**你看，第九部和第十部，就这样接上了。**

## 10.8　回到 CoinJar：让它能用浏览器直接打开

把这一部学的合在一起，我们给 CoinJar 加上"网页版"——从此不装 App，浏览器打开网址就能用。

```python
# CoinJar 服务器（再升级：既能返回数据，也能返回网页）

数据库 = 连接数据库("coinjar_db")

函数 启动服务器():
    服务器 = 创建服务器程序()
    服务器.监听端口(443)
    
    # ===== 网页路由：返回"能看能点"的界面 =====
    
    @服务器.路由("GET /")
    函数 首页():
        # 返回登录/欢迎页（静态网页）
        返回响应(读取文件("首页.html"), 类型="text/html")
    
    @服务器.路由("GET /我的账本")
    函数 账本页(请求):
        # 动态网页：查出这个用户的账，拼进网页
        用户ID = 请求.用户ID
        账目列表 = 数据库.查询("SELECT * FROM 账目表 WHERE 用户ID=?", [用户ID])
        网页 = 渲染模板("账本.html", 账目=账目列表)  # 把数据拼进网页模板
        返回响应(网页, 类型="text/html")
    
    # ===== 数据路由：供网页里的 JS 调用（第八部的 API）=====
    
    @服务器.路由("POST /账目")
    函数 记账(请求):
        # 网页上点"记一笔"时，JS 会调这个 API
        数据库.执行("INSERT INTO 账目表 ...", ...)
        返回响应("记账成功", 状态码=201)
    
    服务器.永久运行()
```

注意这个升级后的服务器，**同时提供两类东西**：

1. **网页**（`GET /`、`GET /我的账本`）——给浏览器看的界面；
2. **数据 API**（`POST /账目`）——给网页里的 JS 调用的接口。

于是用户的完整体验变成了：

```
1. 用户打开浏览器，输入 coinjar.example.com，回车
2. 浏览器向服务器请求首页（GET /）
3. 服务器返回网页，浏览器画出来——用户看到 CoinJar 界面
4. 用户输入"午饭 18"，点击"记一笔"
5. 网页里的 JS 被触发（第五部 事件），向服务器发 POST /账目（第八部 请求）
6. 服务器收到，存进数据库（第九部）
7. 服务器返回"记账成功"
8. 网页 JS 收到响应，刷新页面上的账目列表
9. 用户看到账本里多了一笔——全程没装任何 App
```

**CoinJar 现在有了网页版**——任何人，任何设备，只要有浏览器，打开网址就能用。它的触角，从"装了 App 的人"，扩展到了"全世界能上网的人"。

## 10.9　本章小结与断点预告

**这一章，我们让服务器学会了把"网页"送到浏览器：**

- 不想装 App，打开网址就能用——这需要服务器给浏览器送回一个"能看能点"的网页。
- **浏览器**是一个**通用客户端**：取网页 + 画网页。因为所有网页遵守同一套约定，一个浏览器能画出任何网站——这是"约定"威力的极致体现。
- 一次"打开网址"，背后是第七、八部学的全套：域名→IP→端口→请求→响应。**浏览器就是一个会画界面的客户端。**
- 网页由三样组成：**HTML（骨架/内容）+ CSS（皮肤/样式）+ JS（动作/交互）**。
- 服务器"送网页"，就是第八部的"返回响应"，只是内容类型标记为 `text/html`。
- **静态网页**（人人一样，现成的）vs **动态网页**（按你的数据现场拼出来，依赖第九部的数据库）。
- CoinJar 有了网页版：服务器同时提供"网页"和"数据 API"，全世界有浏览器的人都能用。

**但是，一个微妙又关键的断点浮现了。**

我们刚才说，网页里的 JS 会"向服务器发请求"。可你有没有仔细想过这件事的**结构**？

> 网页（在你浏览器里跑）和服务器（在云端跑），是**两个分开的世界，隔着网络**。
> 网页负责"显示和交互"（前厅），服务器负责"数据和逻辑"（后厨）——
> 这不就是第五部的"前厅与后厨"吗？
> 只是这一次，**前厅和后厨被一道网络的鸿沟，劈成了两半，分别跑在两台机器上。**
>
> **断点：被网络劈开的"前厅"（网页）和"后厨"（服务器），到底怎么分工、怎么隔着网络协作？**
> 网页上点一下，怎么传到服务器？服务器应答后，网页怎么更新？

这就是"前端与后端"的故事——第五部的分层思想，在网络尺度上的重演。

> 我们将看到，第五部那对"前厅与后厨"，是如何被一道网络鸿沟切成"前端"和"后端"的；网页上的一次点击，又是如何穿过网络、抵达服务器、再带着结果回来刷新界面的。
