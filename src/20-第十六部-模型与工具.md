# 第十六部　模型与工具 —— 让 AI 反过来调用你的函数

---

## 16.1　断点：模型说"该记一笔午饭18"，可它没法自己写进数据库

第十五部结尾，我们看清了一个微妙却关键的分工：

> **模型只负责"理解"和"生成语言"，真正"动手执行"的，还是 CoinJar 的代码。**

模型读懂"午饭花了18"，生成一个 JSON `{金额:18, 类目:"午饭"}`。然后呢？是 CoinJar 的代码**手动**接住这个 JSON，**手动**调用 `数据库.执行()` 把它写进去。

当任务简单时，这种"手动接力"还行。可一旦任务变复杂，就崩了。回顾那个例子：

> 用户说："查一下这个月外卖花了多少，如果超过 1000 就提醒我。"

这一句话，需要好几步、好几个函数：
1. `查询账目(类目="外卖", 月份="本月")`
2. `求和(结果)`
3. `比较(总额, 1000)`
4. 如果超了：`发送提醒(...)`

模型能**理解**这个意图、能**想出**这几步该怎么走。但它**不知道** CoinJar 有 `查询账目`、`发送提醒` 这些函数，更**没法亲自调用**它们——它只是个远端的语言大脑，够不到 CoinJar 的代码。

而 CoinJar 的代码呢？它也不可能为"每一种可能的复杂任务"都预先写死一套"手动接力"——用户的话千变万化，写不完。那不就又回到过渡章二批判的"无数个按钮"老路了吗？

> **断点：模型有"大脑"（会理解、会规划），但没有"手"（够不到、不会调用你的函数）；
> 你的代码有"手"（能执行函数），但没有"大脑"（不会理解复杂的自然语言）。
> 怎么把"模型的大脑"和"你代码的手"，连起来？**

解决这个断点的技术，叫**工具调用**（Function Calling / Tool Use）。它是 AI 时代最激动人心的连接——它让模型，**第一次能"指挥"你的代码**。

---

## 16.2　比喻：聪明的军师能出主意，但要靠将士去执行

想象古代的一支军队。

- **军师**（诸葛亮）：足智多谋，能洞察战局、定下妙计——"该派一队人马，从东边小路偷袭粮仓"。但军师**自己不冲锋**，他手无缚鸡之力，亲自去偷袭粮仓只会送命。
- **将士**：武艺高强，能真刀真枪地执行——冲锋、放火、攻城。但将士**自己不定大局**，让他们各自为战，只会一盘散沙。

军队能打胜仗，靠的是**军师出谋、将士执行**的配合：

> 军师说："你，带 500 人，从东路，去烧粮仓。"
> 将士领命，真的带兵去烧了粮仓。
> 烧完回报："粮仓已烧，敌军大乱。"
> 军师根据战报，再定下一步……

请你把这个画面，对应到模型和你的代码：

> - **军师** = 模型：有大脑（会理解、会规划），但没有手（不能直接执行）。
> - **将士** = 你的函数（`查询账目`、`记账`、`发提醒`……）：有手（能真正执行），但没大脑（不会自己决定何时该干、干什么）。
> - **工具调用** = 军师对将士下达军令的那套机制：军师说"调哪支队伍、给什么任务"，将士去执行，再把战果报回来。

这就是工具调用的精髓：

> **模型当"军师"——它决定"该调用哪个函数、传什么参数"；
> 你的代码当"将士"——它真正去执行那个函数，再把结果报告给模型。**
>
> 大脑指挥手，手把结果反馈给大脑。两者配合，才能完成复杂任务。

在 AI 的世界里，你提供给模型调用的这些函数，被称为**工具**（tool）。"工具调用"，就是"模型调用你提供的工具"。

## 16.3　工具调用：模型决定"该调哪个函数、传什么参数"

我们把机制讲清楚。工具调用，有一个关键点必须先澄清，否则容易想错：

> **模型并不"亲自执行"函数。它只是"提议"调用——告诉你的代码"我想调用 `查询账目`，参数是 `类目=外卖, 月份=本月`"。真正执行这个调用的，仍然是你的代码。**

为什么是"提议"而非"亲自执行"？因为模型在远端，它够不到你的代码。它能做的，只是**生成一段结构化的"调用请求"**，由你的代码接住、去执行。

整个流程是这样的（先看全貌，下面几节拆细）：

```
1. 你【事先】告诉模型："我这儿有这些工具可用：查询账目、记账、发提醒……"
        ↓
2. 用户说："查一下这个月外卖花了多少"
        ↓
3. 模型【理解】意图，【决定】："我需要调用'查询账目'这个工具，参数是 类目=外卖,月份=本月"
   → 模型生成一个"工具调用提议"：{ 工具: "查询账目", 参数: {类目:"外卖", 月份:"本月"} }
        ↓
4. 你的代码【接住】这个提议，【真正执行】 查询账目(类目="外卖", 月份="本月")
   → 得到结果：1240 元
        ↓
5. 你的代码把结果【回传】给模型："查询账目的结果是 1240 元"
        ↓
6. 模型【根据结果】生成最终回答："这个月外卖花了 1240 元。"
        ↓
7. 回答给用户
```

看清这个分工链：**模型决定"调什么"（第3步） → 你的代码"执行"（第4步） → 结果"回传"给模型（第5步） → 模型据此"继续"（第6步）。**

这是一个"大脑—手—大脑"的来回。模型从不碰你的数据库、不碰你的函数本体，它只是在恰当的时候说"请帮我调用这个"，然后等你把结果递回来。

## 16.4　角色反转：第一部是人写代码调函数，现在是 AI 来调函数

现在，请你站到全书的高度，看清这一部发生了一件多么深刻的事。

回到**第一部**。那时，是谁决定"调用哪个函数、传什么参数"？

> **是人（程序员）。**
> 程序员写下 `结果 = 算服务费(账目)`——是人，在写代码时，决定了"这里要调 `算服务费`，参数是 `账目`"。
> 函数调用的"决策者"，是写代码的人。

而现在，工具调用带来了一次**惊天的角色反转**：

> **决定"调用哪个函数、传什么参数"的，不再是人，而是模型（AI）。**
> 人不再需要预先写死 `算服务费(账目)`——
> 人只要说一句"算一下服务费"，**模型自己决定**去调 `算服务费`、自己决定参数是什么。

让我们把这个反转，画成对比：

```
第一部（传统）：
  人 在写代码时 → 决定调用 算服务费(账目) → 程序执行
  （决策者：人。决策时机：写代码时。）

第十六部（AI）：
  用户 说一句话 → 模型 在运行时 决定调用 算服务费(账目) → 程序执行
  （决策者：模型。决策时机：运行时，根据用户的话临场决定。）
```

这是"调用"这个全书最核心概念的、最戏剧性的一次放大：

> 第一部：**人**调用函数（决策权在人，写死在代码里）。
> 第十六部：**AI** 调用函数（决策权交给了模型，运行时动态决定）。
>
> 从"人指挥代码"，到"AI 指挥代码"——
> **软件第一次，能根据自然语言，自己决定调用自己的哪些能力。**

这就是为什么工具调用如此激动人心。它让程序从"按固定逻辑执行人写好的调用"，进化到"根据用户的意图，由 AI 临场编排该调用什么"。CoinJar 不再需要为每个功能配一个按钮、配一段"手动接力"代码——它只要把所有能力（函数）作为"工具"交给模型，剩下的"什么时候调哪个"，模型自己搞定。

## 16.5　把你的函数"描述"给模型：工具描述就是给 AI 看的接口

模型怎么知道 CoinJar 有哪些工具可用？又怎么知道每个工具要传什么参数？

靠你**事先把每个函数"描述"给模型**。这个描述，叫**工具描述**（tool definition）。它长这样：

```python
工具列表 = [
  {
    "名称": "查询账目",
    "说明": "查询用户某个类目、某个时间段的账目。当用户想知道某项支出花了多少时使用。",
    "参数": {
      "类目": "字符串，比如 '外卖'、'交通'、'购物'",
      "月份": "字符串，比如 '本月'、'上月'、'2026-05'"
    }
  },
  {
    "名称": "记账",
    "说明": "记录一笔新的支出。当用户说花了多少钱时使用。",
    "参数": {
      "金额": "数字",
      "类目": "字符串",
      "日期": "字符串，默认今天"
    }
  },
  {
    "名称": "发送提醒",
    "说明": "给用户发一条提醒消息。当需要提醒用户某事时使用。",
    "参数": { "消息内容": "字符串" }
  }
]
```

请你仔细看这个"工具描述"，它包含三样东西：

- **名称**：函数叫什么（模型用它来指明"我要调这个"）；
- **说明**：这个函数是干什么的、什么时候该用它（模型靠它来判断"现在该不该调这个"）；
- **参数**：要传什么参数、每个参数是什么意思（模型靠它来"填对参数"）。

现在请你认出这位贯穿全书的老朋友——**这就是"接口"！**

> 回想第二部：**模块接口**告诉调用者"我有哪些函数、每个函数叫什么、要传什么参数"。
> 回想第八部：**API 文档**告诉客户端"服务器有哪些端点、每个要传什么"。
> 现在第十六部：**工具描述**告诉模型"我有哪些工具、每个工具叫什么、要传什么参数"。
>
> **它们是同一种东西——"接口"，即'我能干什么、你该怎么用我'的说明书。**
> 只不过：
> - 模块接口，是写给**程序员**看的（人读）；
> - API 文档，是写给**其他程序的开发者**看的（人读）；
> - 工具描述，是写给**模型（AI）**看的（AI 读）！

这是"接口"思想最奇妙的一次放大——**接口的"读者"，第一次从"人"变成了"AI"。** 你写工具描述时，要站在"模型会怎么理解这段话"的角度去写：说明要清楚（模型才知道何时调用）、参数要明确（模型才能填对）。这其实又是"提示词工程"（15.5）——因为工具描述，本质上也是你对模型说的话的一部分。

> **一个深刻的统一**：在 AI 时代，"接口"和"提示词"开始融合了。
> 你给模型的工具描述，既是"接口"（定义能力），又是"提示词"（用自然语言写给 AI 看）。
> 第二部的"接口"和第十四、十五部的"提示词"，在这里合流了。

## 16.6　一次工具调用的完整闭环：模型提议 → 程序执行 → 结果回传模型

把那个复杂任务——"查一下这个月外卖花了多少，超过 1000 就提醒我"——完整走一遍，看工具调用的闭环怎么转。注意，这个任务需要**多次**工具调用，模型会一步步来：

```
【第 1 轮】
用户："查一下这个月外卖花了多少，如果超过1000就提醒我"
  ↓ CoinJar 把用户的话 + 工具列表，一起发给模型
模型思考："我需要先查外卖花了多少。" 
模型提议：调用 查询账目(类目="外卖", 月份="本月")
  ↓ CoinJar 接住提议，真正执行
CoinJar 执行：查询账目(类目="外卖", 月份="本月") → 数据库返回 1240
  ↓ CoinJar 把结果回传给模型
"查询账目的结果：1240 元"

【第 2 轮】
模型收到结果，继续思考："1240 > 1000，超了，用户要我提醒。"
模型提议：调用 发送提醒(消息内容="本月外卖已花1240元，超过1000元预算，请注意！")
  ↓ CoinJar 接住提议，真正执行
CoinJar 执行：发送提醒(...) → 提醒已发出
  ↓ CoinJar 把结果回传给模型
"发送提醒的结果：成功"

【第 3 轮】
模型收到结果，判断："任务完成了。"
模型生成最终回答："本月外卖共 1240 元，已超过 1000 元预算，我已经给你发了提醒。"
  ↓
回答给用户
```

请你看清这个**闭环**的精妙：

> 它是一个 **"模型提议 → 程序执行 → 结果回传 → 模型再提议……"** 的循环。
> 模型像军师，看一眼战报（上一步结果），定下一道军令（下一个工具调用）；
> 程序像将士，执行军令，回报战果；
> 如此往复，直到军师说"任务完成"。

这个循环，正是第十八部"智能体（Agent）"的雏形——一个能"思考—行动—观察—再思考"的循环。这一部我们先让模型能调一次、两次工具；到第十八部，我们会让这个循环真正"自主"地转起来，去完成开放式的复杂任务。

还有一处呼应：这个"提议→执行→回传"的来回，像不像第五部、第十一部、第十三部的**回调**？

> - 第五部：数据变了，"喊"界面刷新。
> - 第十三部：支付完成，支付平台"喊"你的服务器。
> - 第十六部：模型需要数据，"喊"你的代码去执行工具，执行完"喊回"模型。
>
> 都是"一方需要另一方配合，喊一声、等回应"的协作模式。只是这一次，发起"喊"的，是 AI。

## 16.7　安全边界：绝不能让模型为所欲为

工具调用威力巨大——它让模型能"指挥"你的代码。但**威力越大，风险越大**。这一节是这一部的安全核心，必须刻进脑子。

想想看：你把 `记账`、`查询账目`、`发送提醒` 这些工具交给了模型。模型现在能调用它们。那么问题来了：

> **如果你不小心，把 `删除所有账目`、`转账`、`删除用户` 这种危险的工具也交给了模型，会发生什么？**
>
> 而模型，是会"犯错""幻觉""被误导"的（第十四、十五部反复强调）。
> 万一模型误判用户意图，或者被用户的恶意输入"骗"了，提议调用 `删除所有账目`……
> 而你的代码不加判断，照单全收地执行了……
> **后果不堪设想。**

所以有一条铁律：

> **绝不能让模型为所欲为。模型的每一个工具调用提议，都要经过你的代码"审核"后，才能执行。**

具体怎么设防？这又是全书安全主线的延续和汇合：

**① 最小授权——只给模型必要的工具。**
> 这是第六部"权限"思想：操作系统只给应用必要的权限。
> 这里：只把"安全的、必要的"工具交给模型。危险操作（删库、转账）**根本不放进工具列表**，模型就算想调也调不到。

**② 危险操作要人工确认。**
> 涉及钱、涉及删除等不可逆操作，模型提议后，**不要直接执行，先弹给用户确认**："AI 建议给小李转账 200 元，确认吗？" 用户点了确认，才真正执行。
> 人，始终是危险操作的最后一道闸门。

**③ 永远验证模型给的参数。**
> 这是第十一部"永远不要相信前端"、第十五部"不盲信模型"的延续。
> 模型提议 `记账(金额=-99999)`？你的代码必须检查"金额合不合法"，不合法就拒绝。
> **模型的提议，等同于"不可信的输入"，必须在执行前过一遍安全检查。**

**④ 限制工具的能力范围。**
> 比如 `查询账目` 这个工具，在代码里要**强制只能查"当前登录用户"的账**（用第十二部的身份）——哪怕模型提议"查所有人的账"，工具本身也做不到越界。

请你看清这条安全主线，是怎么一路贯穿全书、到这里达到高潮的：

> 第六部：操作系统在边界上，审核应用的每个系统调用（按权限放行）。
> 第十一部：后端在边界上，审核前端来的每个请求（永远不信前端）。
> 第十二部：服务器在边界上，审核用户的每个操作（按角色授权）。
> 第十六部：你的代码在边界上，审核**模型**的每个工具调用提议（绝不让 AI 为所欲为）。
>
> **同一种"在边界上设关卡、审核来自不可信一方的请求"的思想——
> 而 AI，正是一个强大却'不完全可信'的新的请求方。**

随着 AI 能调用的工具越来越多、能力越来越大，这条安全边界，只会越来越重要。**给 AI 装上手的同时，必须给它套上缰绳。** 这是 AI 时代每个开发者的必修课。

## 16.8　回到 CoinJar：让 AI 助手真正能记账、查账、算账

把这一部的全部，落到 CoinJar 上，让它的 AI 助手第一次"长出手"。

```python
# CoinJar 后端：给 AI 助手装上"工具"

# —— ① 定义工具列表（给模型看的"接口"，16.5）——
工具列表 = [
  {
    "名称": "记账",
    "说明": "记录一笔支出。用户说花了多少钱时用。",
    "参数": {"金额": "数字", "类目": "字符串", "日期": "字符串，默认今天"}
  },
  {
    "名称": "查询账目",
    "说明": "查询某类目某时段的支出总额。用户问花了多少时用。",
    "参数": {"类目": "字符串", "月份": "字符串"}
  },
  {
    "名称": "发送提醒",
    "说明": "给用户发提醒。",
    "参数": {"消息内容": "字符串"}
  }
  # 注意：危险操作（删除所有账目、转账）【不】放进来（16.7 最小授权）
]

# —— ② 工具的"真正实现"（将士，由你的代码执行）——
函数 执行工具(工具名, 参数, 用户ID):
    # 安全检查：每个工具都强制只操作"当前用户"的数据（16.7 限制范围）
    if 工具名 == "记账":
        金额 = 参数["金额"]
        if 金额 <= 0 or 金额 > 1000000:          # 验证参数（16.7 不盲信模型）
            return "金额不合法，拒绝执行"
        数据库.执行("INSERT INTO 账目表 ...", [用户ID, 金额, 参数["类目"], ...])
        return "记账成功"
    elif 工具名 == "查询账目":
        总额 = 数据库.查询("SELECT SUM(金额) FROM 账目表 WHERE 用户ID=? AND 类目=? ...",
                          [用户ID, 参数["类目"]])  # 强制限定 用户ID（身份隔离）
        return f"{总额} 元"
    elif 工具名 == "发送提醒":
        发提醒给用户(用户ID, 参数["消息内容"])
        return "提醒已发送"

# —— ③ 主循环：模型提议 → 执行 → 回传 → 再提议（16.6 闭环）——
@服务器.路由("POST /AI助手")
函数 AI助手(请求):
    用户ID = 检查身份(请求)
    对话历史 = [{"角色": "用户", "内容": 请求.body.用户输入}]
    
    循环:                                          # 可能多轮工具调用
        回答 = 模型API.调用(
            消息 = 对话历史,
            工具 = 工具列表,                        # 把工具描述一起发给模型
            API密钥 = 模型API密钥
        )
        
        if 回答.有工具调用提议:                      # 模型说"我要调某个工具"
            工具名 = 回答.工具调用.名称
            参数 = 回答.工具调用.参数
            
            结果 = 执行工具(工具名, 参数, 用户ID)    # 你的代码真正执行（含安全检查）
            
            对话历史.追加({"角色": "助手", "工具调用": 回答.工具调用})
            对话历史.追加({"角色": "工具", "内容": 结果})  # 把结果回传给模型
            继续循环                                 # 让模型根据结果决定下一步
        else:                                       # 模型给出最终回答了
            返回响应({"AI回复": 回答.内容}, 状态码=200)
            退出循环
```

现在，李姐和 CoinJar 的对话可以是这样的：

```
李姐："上午买菜花了 45，下午打车 20"
AI 助手：（提议调用 记账(45,"买菜") → 执行 → 回传 → 再提议 记账(20,"交通") → 执行）
        "好的，已记两笔：买菜 45 元，交通 20 元。"

李姐："这个月外卖花了多少？超过 1000 提醒我一下"
AI 助手：（提议 查询账目("外卖","本月") → 执行得 1240 → 判断超了 → 提议 发送提醒 → 执行）

李姐："这个月总共花了多少？跟上个月比呢？"
```

**CoinJar 的 AI 助手，第一次"长出了手"。** 它不再只是"理解然后让代码手动接力"，而是能**自己决定调用哪些工具、按什么顺序、传什么参数**，真正地记账、查账、算账、提醒。过渡章二那个"界面膨胀、功能越多按钮越多"的难题，被彻底化解了——CoinJar 现在只需要一个对话框，所有功能由 AI 临场编排调用。

## 16.9　本章小结与断点预告

**这一章，我们完成了 AI 时代最激动人心的连接——让模型反过来调用你的代码：**

- 模型有"大脑"无"手"，你的代码有"手"无"大脑"——**工具调用**把两者连起来。
- 比喻：模型是**军师**（出谋、不执行），你的函数是**将士**（执行、不决策）。模型决定"调什么工具、传什么参数"，你的代码真正执行。
- **角色反转**：第一部是**人**决定调用哪个函数（写死在代码里）；现在是 **AI** 在运行时、根据用户的话，**自己决定**调用哪个函数——"调用"思想最戏剧性的放大。
- **工具描述就是给 AI 看的"接口"**：接口的读者，第一次从"人"变成了"AI"；接口与提示词，在这里合流。
- **闭环**：模型提议 → 程序执行 → 结果回传 → 模型再提议……这是第十八部 Agent 的雏形，也是"回调"思想的延续。
- **安全铁律**：绝不让模型为所欲为——最小授权、危险操作人工确认、永远验证模型给的参数、限制工具能力范围。这是全书"边界审核"安全主线的高潮：**AI 是一个强大却不完全可信的新请求方。**
- CoinJar 的 AI 助手"长出了手"，能自主记账、查账、算账、提醒，一个对话框取代了所有按钮。

**但是，一个新的、很根本的断点浮现了。**

CoinJar 的 AI 助手现在能调工具、查账目了。可你有没有注意到——**它查的，必须是"已经存在你数据库里"的结构化数据**（金额、类目、日期）。

如果李姐问的是一个更"开放"的问题呢：

> "我上次买那个相机，到底花了多少来着？"
> "我这半年在'养猫'上前前后后花了多少？猫粮、猫砂、看病……"

这些问题里，"相机""养猫"可能并不是 CoinJar 里一个规规矩矩的"类目"——它们可能散落在各种备注、各种类目里。模型要回答，得**先在你乱七八糟的真实账目里，按'意思'找出相关的那些笔**。

> **断点：模型能调工具查"结构化的、它知道怎么查的"数据，可它不了解"你的"全部情况——你那些自由记录的、非结构化的、需要按'含义'去匹配的数据。怎么让模型真正"读懂你的账本"？**

这就需要把模型，连上"你的私有数据"——而且是按"语义"去连。

> **下一站，第十七部：模型与知识。**
> 我们将看到，怎么让模型"读懂"你的真实账本——通过**检索增强（RAG）**和**语义检索**，让 AI 基于你的私有数据来回答，而不是凭空生成。你会发现，这是"寻址"思想一次奇妙的放大：从"按地址找"，到"按意思找"。
