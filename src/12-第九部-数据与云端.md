# 第九部　数据与云端 —— 上传的数据如何存进服务器

---

## 9.1　断点：数据躺在服务器的内存里，一重启就灰飞烟灭

第八部结尾，我们留下了一个致命断点：

CoinJar 的账目成功"飞"到了服务器——客户端发请求、服务器收到、存进了 `账目列表 = []`。可这个列表在**内存**里。服务器一重启（维护、崩溃、断电……），内存清空，**一个月的账目，瞬间人间蒸发。**

这不是小问题。想象一下：

- 你辛苦记了一年的账，服务器凌晨重启一次，早上醒来全没了；
- 一万个用户的数据都在服务器内存里，服务器崩溃，一万人的数据同时蒸发；
- 你根本不知道服务器什么时候会重启——可能是明天，可能是下一秒。

> **断点：数据到了云端，但没有"落地"。它只是暂时躺在内存这张"临时工作台"上，随时可能消失。**
> 必须把它，真正存进服务器的**硬盘**——一个断电也不会丢的地方。

这就是这一部的主题：**让上传到服务器的数据，真正永久地保存下来。**

---

## 9.2　比喻：从随手记的便签，到银行那本永久的总账

想象你去银行存钱。柜员接待你（收到请求），你说"存 1000 块"（上传数据）。

**糟糕的做法：** 柜员在一张**便签纸**上记下"某某存了 1000"，然后把便签夹在工作台上。你走了。下班时，清洁工把工作台收拾干净，便签扔了。第二天你来取钱——"对不起，没记录"。

**正确的做法：** 柜员把这笔存款，记进银行那本**永久的总账本**里——一本厚厚的、锁在保险柜里的、几十年都不会丢的账本。哪怕柜员换班、银行停电、系统重启，只要那本账本还在，你的 1000 块就永远有记录。

内存就是那张**便签**——快、方便、但一擦就没；
硬盘（更准确说，**数据库**）就是那本**永久总账**——慢一点，但可靠、持久、断电也在。

服务器要做的，就是把客户端上传的数据，**从便签（内存）抄进总账（硬盘/数据库）**。这样，哪怕服务器程序重启一万次，数据都在硬盘里安安稳稳地躺着。

## 9.3　数据库是什么：服务器上专门管"存与取"的大管家

你可能在想：第六部不是讲过"文件系统"吗？服务器也有硬盘、也有文件系统，直接把账目写进一个文件不就完了？

**技术上可以，但不够好。** 因为服务器面对的问题，比单机复杂得多：

- **多人同时写**：此刻可能有一万个用户同时在记账——一万个客户端同时向服务器发请求，服务器要**同时**处理这些"存账"操作。如果只是往一个文件里写，谁先写、谁后写、会不会写乱、会不会把对方的数据覆盖掉？
  
- **按条件查**：用户说"查我去年 10 月的账"，服务器要从几百万笔账里，精确地捞出"你的、去年 10 月的"那几笔。如果账目只是一个大文件，服务器得从头到尾扫一遍——太慢了。

- **保证不丢**：万一服务器写到一半崩溃了，怎么保证数据不会"写了一半、坏掉了"？万一硬盘坏了，怎么保证有备份？

这些问题，单机时代的"文件系统"能应付（因为只有一个用户、数据量小、很少崩溃）。但到了云端服务器——**几百万用户、几十亿条数据、24 小时不停运转**——文件系统扛不住了。

所以服务器上，有一个**专门的、比文件系统更强大的"管家"，专职负责"存与取"**。它就是**数据库**（database）。

> **数据库，是一个专门管理大量数据的"存、取、查、改"的程序。**
> 它跑在服务器上，像一个管家，替服务器：
> - **存**：把数据可靠地写进硬盘，保证不丢；
> - **取**：按你的要求（"我要 2025 年 10 月的账"），精确又快速地捞出来；
> - **处理并发**：同时有一万人要存数据，它能保证不乱；
> - **保证一致**：写到一半崩溃了，它能自动回滚，不会留下"坏掉一半的数据"。

数据库之于服务器，就像第六部"操作系统"之于应用——它是服务器向下依赖的那个"更底层的强大存在"。

常见的数据库有很多（MySQL、PostgreSQL、MongoDB……），名字你**不需要记**。你只需记住：**数据库 = 云端服务器的"永久保险柜" + 高效管家。**

## 9.4　一次"上传"的完整旅程：从你的手机到服务器的硬盘

现在我们完整地走一遍：你在手机上记一笔"午饭 18 元"，它是怎么最终躺进服务器硬盘、永久保存的。

```
1. 手机客户端
   你点"记一笔"，输入"午饭 18 元"
   ↓
   客户端构造请求：
   POST https://coinjar.example.com:5000/账目
   数据：{ "金额": 18, "类目": "午饭", "日期": "2026-06-26" }
   ↓
   发送（第七部的网络层接管）

2. 网络
   数据包一跳接一跳，穿过路由器，抵达服务器机器
   ↓

3. 服务器程序（内存中）
   收到请求，触发 记账() 函数
   ↓
   服务器说："好，我要把这笔账存下来。但不能只放内存，得存进数据库。"
   ↓
   服务器向数据库发指令（SQL 或其他查询语言）：
   "INSERT INTO 账目表 VALUES (18, '午饭', '2026-06-26', 用户ID)"
   ↓

4. 数据库程序（也在服务器机器上跑着）
   收到指令，把这笔账**写进硬盘**
   - 追加到数据文件里
   - 更新索引（下次查得快）
   - 记日志（万一崩溃能恢复）
   ↓
   数据库回复服务器："写入成功"
   ↓

5. 服务器程序
   收到数据库的确认，向客户端返回响应：
   { "状态码": 201, "内容": "记账成功" }
   ↓

6. 网络
   响应数据包返回手机
   ↓

7. 手机客户端
   收到响应，显示"记账成功"
```

**关键的那一步，在第 4 步——数据库把数据写进了硬盘。** 从这一刻起，哪怕服务器程序崩溃、重启、断电，这笔账都**永远在硬盘里了**。下次服务器重启，数据库程序一启动，就能从硬盘读回所有数据。

请你看清这里的层次：

```
客户端（手机） 
   ↕ 网络请求
服务器程序（内存中，处理业务逻辑）
   ↕ 数据库指令
数据库程序（内存 + 硬盘，管"存与取"）
   ↕ 读写硬盘
硬盘（物理存储）
```

这又是一次**分层与提要求**的重演：

> - 第六部：应用 → 操作系统 → 硬件（单机内的三层）
> - 第九部：客户端 → 服务器 → 数据库 → 硬盘（云端的四层）
>
> **每一层都在向下一层"提要求"，自己不直接碰更底层的东西。**
> 客户端不直接碰数据库，服务器不直接碰硬盘——各司其职，层层分工。

## 9.5　读取：服务器怎么按需把你的账目捞回来

存进去了，还得能取出来。用户打开 App，点"查看我的账目"，服务器怎么把它从数据库里捞回来？

```
1. 客户端发请求：
   GET /账目?用户=你的ID&月份=2026-06

2. 服务器收到，向数据库查询：
   "SELECT * FROM 账目表 WHERE 用户ID=你的ID AND 日期 LIKE '2026-06%'"
   （意思：从账目表里，筛出"属于你、且是 2026 年 6 月"的所有记录）

3. 数据库：
   - 根据索引快速定位（不用扫全表，快！）
   - 从硬盘读出匹配的记录
   - 返回给服务器：[{18, "午饭", "2026-06-26"}, {30, "打车", "2026-06-15"}, ...]

4. 服务器收到，构造响应：
   { "状态码": 200, "数据": [账目列表] }

5. 客户端收到，显示在界面上
```

**请你注意**：服务器向数据库"提要求"的方式——用一种叫 **SQL**（Structured Query Language，结构化查询语言）的语言，说"我要查什么、筛什么条件"。数据库听懂了，去硬盘里翻，翻出来交给服务器。

这又是"接口与约定"的重演：

> - 第二部：模块 A 调用模块 B，靠"函数签名"这套约定；
> - 第八部：客户端请求服务器，靠"API"这套约定；
> - 第九部：服务器查询数据库，靠"SQL"这套约定。
>
> **不同层次、不同组件之间的对话，都需要一套"双方都懂"的语言（约定）。**

SQL 的细节你**完全不必记**。你只需知道：服务器和数据库之间，有一套"提要求 + 拿结果"的对话模式——和客户端与服务器之间的"请求 + 响应"，**骨架一模一样**。

## 9.6　多人同时写：当你和家人同一秒都记了一笔

云端服务器最复杂的场景之一：**并发**（concurrency）——很多人同时在操作。

想象：此刻你在记"午饭 18"，你的爱人同一秒也在记"打车 30"。两个请求几乎同时到达服务器，服务器几乎同时向数据库发两条 INSERT 指令。

**会不会乱？会不会一条覆盖另一条、或者写成一半你一半我的怪胎？**

好消息：**数据库天生就是为了解决这个问题而生的。** 它内置了一整套"并发控制"机制——保证哪怕一万个写操作同时来，每一条都能**独立、完整、不乱**地写进硬盘。

具体怎么做到的（锁、事务、隔离级别……）非常复杂，但你**不需要理解细节**。你只需记住：

> **数据库是多人共用的"公共保险柜"，它内置了"排队取号、互不干扰"的机制。**
> 你只管发指令，数据库保证不会乱。

这又呼应了第六部的一个影子：

> 第六部：多个应用（微信、浏览器、CoinJar）同时向操作系统请求"读文件、写文件"，操作系统内部有调度机制，保证不会乱。
>
> 第九部：多个客户端同时向数据库请求"存数据、查数据",数据库内部有并发控制，保证不会乱。
>
> **都是：一个公共的、强大的管家，服务着很多同时来的请求者，内部机制保证秩序。**

从"一台机器的操作系统"，到"云端的数据库"——同一种"公共管家"的角色，在更大的尺度上重演。

## 9.7　数据是真正的资产：备份、一致与可靠

到这里，数据终于"落地"了——存进了服务器硬盘。但云端服务有一个单机没有的关键要求：**绝对不能丢数据。**

单机时代，你的账本文件丢了，最多你一个人倒霉。云端时代，服务器的数据库丢了，**几百万用户的数据同时蒸发**——这是灾难性的事故。

所以云端数据库有一整套"保命"机制：

### 备份（Backup）

数据库不会只把数据存一份。它会定期把整个数据库**复制**到别的硬盘、别的机器、甚至别的城市的机房。万一主硬盘坏了，立刻切换到备份。

> 这像是：银行不会只有一本总账，它会每天把总账复印一份，锁进另一个保险柜。

### 一致性（Consistency）

数据库保证：**要么一件事完整地做完，要么完全不做，绝不留下"做了一半"的烂摊子。**

比如：你要转账 100 块给朋友——这需要两步："你的账户 -100"+"朋友的账户 +100"。如果数据库写完第一步、第二步还没写，突然崩溃了，那就坏了——你的钱少了，朋友的钱没加，100 块人间蒸发。

数据库的**事务**（transaction）机制保证：这两步要么一起成功、要么一起回滚（撤销），**绝不会留下中间状态**。

> 这又是"要么成功、要么失败，不留半吊子"思想的体现——第六部"系统调用可能失败"就埋下了这条线。

### 可靠（Reliability）

数据库写数据时，不只是"扔进硬盘就完事"——它会先写**日志**（log），记下"我要写什么"。万一写到一半崩溃了，重启后读日志，就知道"刚才在干什么、干到哪了"，能自动恢复或回滚。

这些机制的细节，你完全不必懂。你只需记住一个道理：

> **数据是云端服务的命根子。**
> 单机时代，数据丢了最多你自己倒霉；云端时代，数据丢了，是公司倒闭级别的灾难。
> 所以云端对"数据不能丢"的投入，是单机的一百倍、一千倍。
>
> 数据库，就是这份投入的核心。

## 9.8　回到 CoinJar：给服务器接上数据库，账目永久落地

理论讲完了，让 CoinJar 动手。这一次，我们把第八部那个"存内存"的服务器，升级成"存数据库"。

```python
# CoinJar 账本服务器（升级版：接入数据库）

数据库 = 连接数据库("coinjar_db")  # 连接到数据库程序

函数 启动服务器():
    服务器 = 创建服务器程序()
    服务器.监听端口(5000)
    
    # API 1: 查账目
    @服务器.路由("GET /账目")
    函数 查账目(请求):
        用户ID = 请求.用户ID  # 从请求里拿到"是谁在查"（第十二部会讲怎么拿）
        
        # 向数据库查询（SQL）
        账目列表 = 数据库.查询(
            "SELECT * FROM 账目表 WHERE 用户ID = ? ORDER BY 日期 DESC",
            参数 = [用户ID]
        )
        
        返回响应(账目列表, 状态码=200)
    
    # API 2: 记一笔账
    @服务器.路由("POST /账目")
    函数 记账(请求):
        新账目 = 请求.body
        用户ID = 请求.用户ID
        
        # 向数据库插入（SQL）
        数据库.执行(
            "INSERT INTO 账目表 (用户ID, 金额, 类目, 日期) VALUES (?, ?, ?, ?)",
            参数 = [用户ID, 新账目.金额, 新账目.类目, 新账目.日期]
        )
        
        # 关键！数据库内部会把这条记录写进硬盘
        # 从这一刻起，哪怕服务器重启，这笔账都永远在了
        
        返回响应("记账成功", 状态码=201)
    
    # API 3: 删一笔账
    @服务器.路由("DELETE /账目/{账目ID}")
    函数 删账(账目ID, 请求):
        用户ID = 请求.用户ID
        
        # 向数据库删除（SQL）
        数据库.执行(
            "DELETE FROM 账目表 WHERE ID = ? AND 用户ID = ?",
            参数 = [账目ID, 用户ID]
        )
        
        返回响应("删除成功", 状态码=200)
    
    显示("服务器已启动，数据库已连接，账目将永久保存")
    服务器.永久运行()
```

对比第八部的代码，核心变化只有一处：

**第八部（存内存）：**
```python
账目列表.添加(新账目)  # ← 数据在内存里，重启就没了
```

**第九部（存数据库）：**
```python
数据库.执行("INSERT INTO 账目表 ...")  # ← 数据进硬盘了，永久保存
```

服务器的业务逻辑（"收请求→处理→返回响应"）**没变**，只是把"存哪里"从内存换成了数据库。这就是**分层的好处**——换掉底层（存储），不影响上层（业务）。

从此，CoinJar 的账目，真正在云端落地了。你记一笔、存进服务器、服务器存进数据库、数据库写进硬盘——**四层接力，最终抵达那个"断电也不会丢"的地方。**

## 9.9　本章小结与断点预告

**这一章，我们让上传到云端的数据，真正永久地保存了下来：**

- 内存是"临时工作台"，服务器重启就清空——数据必须"落地"到硬盘才永久。
- **数据库**是服务器上专门管"存与取"的大管家——比文件系统更强大，能处理多人并发、按条件查询、保证不丢不乱。
- 一次上传的完整旅程：客户端 → 网络 → 服务器 → **数据库 → 硬盘**。数据库把数据写进硬盘的那一刻，数据永久了。
- 读取也是类似：服务器向数据库发查询（SQL），数据库从硬盘读、返回服务器、服务器返回客户端。
- **多人同时写**：数据库内置并发控制，保证不乱——这是"公共管家"角色在云端的体现（对比第六部的操作系统）。
- **数据是资产**：云端对"不能丢数据"极其重视——备份、事务、日志，一整套机制保驾护航。
- CoinJar 服务器升级：从"存内存"换成"存数据库"，账目永久落地。

**核心认知：数据库 = 第六部"文件系统"的云端放大版。** 单机时代靠文件系统存取数据，云端时代靠数据库——尺度更大、用户更多、要求更高，但"存与取"的本质，没变。

**但是，新的断点立刻浮现。**

CoinJar 现在是一个货真价实的云端应用了：数据永久保存在服务器上，你的手机、家人的电脑都能访问。可你有没有发现一个问题——

> 客户端是个 **App**，用户得先**下载、安装**，才能用。
> 可很多人不想装 App——能不能**打开一个网址，就直接用**？就像你访问淘宝、知乎、B 站，不用装 App,在浏览器里就能用。
>
> **断点：服务器有了、数据有了、客户端也有了，但客户端是个需要安装的 App。能不能不装 App，打开浏览器就用？**

这就需要服务器学会一件新本事——**把"网页"送到浏览器里**。这正是下一部的主题。

> **下一站，第十部：服务器与浏览器。**
> 我们将看到，当你在浏览器地址栏输入 `coinjar.example.com` 并回车，服务器是怎么把一个"能看能点能用"的网页，送到你眼前的。你会发现，这仍然是第八部"请求与响应"的延续——只是这次，服务器响应的不是数据,而是一整个界面。
