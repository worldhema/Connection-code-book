# 第一部　函数与函数 —— 最小的连接

---

## 1.1　断点：一段代码太长了，怎么办？

还记得序章里那个简陋的主角吗？CoinJar，只会记一笔账。

我们先把它现在的样子完整地摊开来看。当你说"今天花了 18 块买午饭"，它内部大概是这样一气呵成地跑下来的：

```
# CoinJar 第一版：所有事情挤在一起

输入文本 = "午饭 18"

# 1. 把输入拆开
部分 = 输入文本.拆分(" ")
项目 = 部分[0]          # "午饭"
金额文本 = 部分[1]      # "18"

# 2. 把金额从文字变成数字
金额 = 把文字转成数字(金额文本)

# 3. 检查一下合不合理
如果 金额 <= 0:
    显示("金额不对")
否则:
    # 4. 记下来
    账目 = { "项目": 项目, "金额": 金额 }
    # 5. 算个税（假设记账要算 6% 服务费）
    服务费 = 金额 * 0.06
    # 6. 拼一句话给用户看
    消息 = "已记录：" + 项目 + " " + 金额 + " 元，服务费 " + 服务费 + " 元"
    显示(消息)
```

这段代码现在还能看。但请你想象一下，CoinJar 慢慢长大：

- 输入的格式越来越多（"午饭 18"、"2024-01-01 午饭 18"、"午饭 ¥18.00"）；
- 检查的规则越来越细（金额不能为负、项目名不能为空、日期不能是未来）；
- 记账后要做的事越来越多（算服务费、更新总额、写日志、刷新界面）……

每多一个需求，这段代码就往下长一截。不出几个月，它会变成一条**几百行、从头垂到尾的瀑布**。

这时候，断点出现了：

> **一段代码太长，会发生什么坏事？**

三件坏事：

1. **读不懂**——你得从第 1 行一路读到第 300 行，才能拼出"它到底在干嘛"。
2. **改不动**——你想改"怎么算服务费"，却得在 300 行里大海捞针。
3. **没法重用**——"把文字转成数字"这件事，别处也要用，可它被埋在这段瀑布的中间，搬不出来。

我们需要的，不是把代码写得更长，而是**把它拆开**——然后让拆开的几块**还能彼此连上**。

这，就是"函数"登场的地方。

## 1.2　比喻：把一件事，拆成几个人接力做

设想你要办一场家宴。

如果只有你一个人，从买菜、洗菜、切菜、炒菜到摆盘上桌，全程一个人从头干到尾——这就是上面那段"垂到底的瀑布"。累，而且一步出错，整桌乱套。

聪明的做法是**分工**：

- 老大负责**买菜**，买回来交给老二；
- 老二负责**洗切**，弄好交给老三；
- 老三负责**下锅**，做好交给老四；
- 老四负责**摆盘上桌**。

每个人只管自己那一小段，**做完就把成果交给下一个人**。

注意这里的两个关键动作：

- **"交给下一个人"**——这就是**调用**：我做完了，喊你来接着干。
- **"把成果交出去"**——这就是**返回**：我把我的产出递给你。

一场原本一个人忙到崩溃的家宴，被拆成了四个清清楚楚的环节，每个环节都能单独检查、单独替换、单独重用（下次买菜还是找老大）。

**函数，就是程序里的"某个负责一小段活儿的人"。**

---

## 1.3　函数是什么：一个有名字的"任务"

把上面那段瀑布里的一小块——"把文字转成数字"——单独拎出来，给它起个名字、围上一个边界，它就成了一个**函数**：

```
函数 把文字转成数字(文字):
    数字 = ... # 具体怎么转，这里先不管
    返回 数字
```

我们逐字拆解这个"人"是怎么定义出来的：

- **函数** ——一个声明，意思是"下面我要定义一个有名字的任务了"。
- **把文字转成数字** ——它的**名字**。名字极其重要，它是别人"喊"它时用的称呼，也是它对外的招牌（看名字就知道它干嘛）。
- **(文字)** ——它的**入口**。括号里是它干活需要的"原料"，叫**参数**。这个函数说："你想让我转换，就得先把那段文字给我。"
- **返回 数字** ——它的**出口**。它干完活，把成果**交回去**。

于是，一个函数就有了清清楚楚的三件事：**一个名字、一个入口、一个出口**。

> 你可以把函数想成一台**专用小机器**：
> 从入口塞进原料（参数），机器内部咔咔运转（函数体），从出口吐出成品（返回值）。
> 而你用它的时候，**根本不用关心机器内部怎么转**——你只要会塞料、会接成品就行。

这就是函数给我们的第一份大礼：**把"怎么做"藏起来，只留下"叫什么、要什么、给什么"。**

---

## 1.4　调用：一个函数怎么"喊"另一个函数

光定义出一台小机器还不够。机器要被**按下开关**，才会运转。

"按下开关"这个动作，就叫**调用**（call）。

```
结果 = 把文字转成数字("18")
```

这一行里发生了一连串精巧的事，我们慢镜头回放：

1. 程序跑到这里，看见 `把文字转成数字(...)`，知道："哦，要去喊那个叫'把文字转成数字'的函数了。"
2. 它把括号里的 `"18"` 作为原料，**递进**那个函数的入口。
3. **程序的控制权，跳进了那个函数内部**——此刻，瀑布主线暂停，跑去执行小机器里的代码。
4. 小机器算完，执行到 `返回`，把成品（数字 18）吐出来。
5. **控制权跳回到调用的地方**，并且 `把文字转成数字("18")` 这一整块，被替换成了它吐出的成品——18。
6. 于是 `结果` 拿到了 18。

这里最值得你记住的一句话是：

> **调用，是程序里"控制权"的一次出借与归还。**
> 我（调用方）暂停下来，把控制权借给你（被调用的函数）；
> 你干完、返回，控制权再还给我，我接着往下走。

序章里说"一个小任务做完了，喊出下一个小任务"——**喊，就是调用**。这就是程序里**最小、最基础的那一种连接**。整本书后面所有更大的连接，骨子里都是它的放大版。

---

## 1.5　参数与返回值：它们之间传递的"货物"

如果说"调用"是两个函数之间架起的一条**通道**，那么在这条通道上来回运送的**货物**，就是**参数**和**返回值**。

- **参数**：调用方 → 函数。是"我给你的原料"。
- **返回值**：函数 → 调用方。是"我还给你的成品"。

```
                参数 "18"  ──────►
   ┌──────────┐              ┌────────────────┐
   │  调用方   │              │ 把文字转成数字  │
   └──────────┘              └────────────────┘
                ◄──────  返回值 18
```

为什么这件事如此重要？因为**正是这一来一回的货物，让两个孤立的函数产生了关系。**

回想 0.2 节那根"孤独的电线头"。一个函数如果**不接收任何参数、也不返回任何东西**，它就几乎是孤立的——很难和别人形成有意义的连接。而参数和返回值，就是给电线头**接上两端**的接线柱：

- 参数，是它的"上游接口"——接收别人的产出；
- 返回值，是它的"下游接口"——把产出交给别人。

一个函数的**返回值**，可以正好成为另一个函数的**参数**。这样一来，函数就能像水管一样**串起来**：

```
金额 = 把文字转成数字( 取出金额部分( 输入文本 ) )
```

读这一行要**从里往外**读：

1. 先把 `输入文本` 交给 `取出金额部分`，它返回 "18"；
2. 这个 "18" 又立刻成为 `把文字转成数字` 的参数；
3. 后者返回数字 18，交给 `金额`。

看见了吗？**一个函数的出口，接上了另一个函数的入口。** 这就是函数之间最自然的连接方式——数据像接力棒一样，一棒传一棒。

## 1.6　调用栈：谁喊了谁，回头怎么找到路

现在有个问题。

老大喊老二，老二喊老三，老三喊老四……一层接一层喊下去。等老四干完了，控制权要"还回去"——可它怎么知道**该还给谁**？老四怎么记得是老三喊的它，而老三又是老二喊的？

程序用一个极其朴素、又极其聪明的办法来记账，叫**调用栈**（call stack）。

"栈"，你就想成一摞盘子：**只能往最上面放，也只能从最上面拿。** 后放上去的，先被拿下来。

每当一个函数**喊**另一个函数，程序就往这摞盘子上**放一个新盘子**，写着"我从这里喊出去的，记得回来找我"。每当一个函数**返回**，就从最上面**拿走一个盘子**，按上面写的地址把控制权还回去。

我们看 CoinJar 的一次调用，盘子是怎么摞起来又拆下去的：

```
主程序 调用 记一笔账(...)
  └─ 记一笔账 调用 解析输入(...)
        └─ 解析输入 调用 把文字转成数字(...)
```

此刻盘子从下到上摞着三层：

```
  ┌────────────────────┐  ← 栈顶（最后喊的，最先返回）
  │  把文字转成数字      │
  ├────────────────────┤
  │  解析输入            │
  ├────────────────────┤
  │  记一笔账            │
  └────────────────────┘  ← 栈底（最早开始的）
```

然后开始"还路"：

1. `把文字转成数字` 返回 → 拿掉最上面的盘子 → 控制权回到 `解析输入`；
2. `解析输入` 返回 → 再拿掉一个 → 控制权回到 `记一笔账`；
3. `记一笔账` 返回 → 再拿掉 → 回到主程序。

**喊出去的顺序，和返回回来的顺序，正好相反。** 最后被喊的，最先返回——就像那摞盘子，最后放上去的最先被拿走。

这也解释了一个你迟早会遇到的现象：当程序出错崩溃时，它常常吐给你一长串东西，叫"调用栈轨迹"（stack trace）。那其实就是**把出事那一刻的整摞盘子，从上到下念给你听**——"我在 A 里出的错，A 是 B 喊的，B 是 C 喊的……"。学会读它，你就能顺着这条连接的线索，一路找到问题的源头。

> 调用栈告诉我们一件深刻的事：**连接不仅要能"接过去"，还要能"找回来"。**
> 函数之间的连接是**双向**的——去的时候靠调用，回的时候靠这摞盘子记下的路。

## 1.7　回到 CoinJar：把"记一笔账"拆成会互相调用的小函数

道理讲完了，我们回到主角身上，亲手做一次拆分。

还记得 1.1 节那段从头垂到尾的瀑布吗？现在我们用"分工"的眼光重看它，会发现它其实在干**四件不同的事**：

1. 把用户输入的一句话**拆解**成项目和金额；
2. **检查**这笔账合不合理；
3. 把它**记录**下来，并算好服务费；
4. 拼一句话**显示**给用户看。

四件事，正好交给四个"人"——四个函数：

```
# 老大：负责解析
函数 解析输入(文本):
    部分 = 文本.拆分(" ")
    项目 = 部分[0]
    金额 = 把文字转成数字(部分[1])      # 注意：这里它又喊了一个更小的函数
    返回 { "项目": 项目, "金额": 金额 }

# 老二：负责检查
函数 检查账目(账目):
    如果 账目["金额"] <= 0:
        返回 假        # 不合理
    返回 真            # 合理

# 老三：负责记录与计算
函数 记录账目(账目):
    服务费 = 账目["金额"] * 0.06
    账目["服务费"] = 服务费
    # （把它存进某个列表，这里先略）
    返回 账目

# 老四：负责显示
函数 报告结果(账目):
    消息 = "已记录：" + 账目["项目"] + " " + 账目["金额"] + " 元，服务费 " + 账目["服务费"] + " 元"
    显示(消息)
```

现在，需要有个"总指挥"把这四个人**串起来**——让他们接力。这个总指挥本身也是一个函数：

```
# 总指挥：负责把四个人接力连起来
函数 记一笔账(输入文本):
    账目 = 解析输入(输入文本)          # ① 喊老大
    如果 检查账目(账目) == 假:          # ② 喊老二
        显示("金额不对")
        返回
    账目 = 记录账目(账目)              # ③ 喊老三
    报告结果(账目)                     # ④ 喊老四
```

请你停下来，对比一下这版和 1.1 节那版瀑布。代码总量其实差不多，甚至更多了。但发生了三个本质的变化：

1. **读得懂了**。看 `记一笔账` 这个总指挥，五行就讲清了整件事的**骨架**："解析 → 检查 → 记录 → 报告"。想看细节，再去翻具体某个函数。**主线和细节分开了。**
2. **改得动了**。想改"服务费怎么算"？只去 `记录账目` 里改，别处一个字都不用动，也不怕碰坏别的逻辑。**每个函数都有了自己的"责任田"。**
3. **能重用了**。`把文字转成数字` 现在是个独立的小机器，CoinJar 里任何地方要把文字转数字，喊它一声就行，不必再抄一遍。

而把这一切缝合起来的，正是本章的主角——**调用**。`记一笔账` 调用四个下属，`解析输入` 又调用 `把文字转成数字`……一条条调用，就是一根根连线。

CoinJar 内部，第一次从"一块铁板"，变成了**一张由函数连成的小网**。

## 1.8　本章小结与断点预告

**这一章，我们建立了全书最基础的那种连接：**

- 一段代码太长会带来三宗罪：读不懂、改不动、不能重用。
- **函数**是解药：它把"一小段活儿"围起来，给它**一个名字、一个入口（参数）、一个出口（返回值）**。
- **调用**是函数之间最小的连接：它是控制权的一次**出借与归还**。
- **参数和返回值**是这条连接上来回运送的**货物**，能让函数像水管一样串起来。
- **调用栈**记下了"谁喊了谁"，保证控制权去得了、也回得来——连接是**双向**的。
- 我们把 CoinJar 从一块铁板，拆成了一张**由函数连成的小网**。

**但是，新的断点又出现了。**

CoinJar 现在有四五个函数，还算清爽。可它要长大——

- 光"解析"就会分裂出十几个函数（解析日期、解析币种、解析备注……）；
- "显示"又会冒出一堆（显示到屏幕、显示成表格、显示成图表……）；
- "存储"还会再来一打……

很快，几十、上百个函数会**平铺**在一起，挤成黑压压的一片。

那时你会面临一个新问题：

> 这么多函数堆在一块儿，**怎么找？怎么归类？** 解析相关的能不能放一堆、显示相关的放另一堆，让它们各回各家？

换句话说——函数太多了，**谁来收纳它们？**

这正是下一种、更大一号的连接要解决的问题。

> **下一站，第二部：模块与模块。**
> 我们将学会把一群相关的函数，打包进一个"抽屉"——也就是**模块**，再看抽屉与抽屉之间，是怎么互相借东西的。
