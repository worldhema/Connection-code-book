# 第十五部　应用与模型 —— 程序如何调用一个 AI

---

## 15.1　断点：模型在哪？CoinJar 怎么把用户的话交给它？

第十四部结尾，留下了一个很实在的问题。

李姐对着 CoinJar 说"午饭花了18"，CoinJar 要把这句话交给模型去理解。可是——**模型在哪？**

它不在李姐的手机里——一个大语言模型，动辄几十 GB、上百 GB，需要极强的 GPU 才能跑起来，手机装不下、也跑不动。

它也不在 CoinJar 自己的服务器里——CoinJar 的服务器就是个普通的云主机（第九部），也没那个算力和成本去养一个模型。

**模型，运行在专门的、极其强大的远端机器上。** 通常是专业 AI 公司（OpenAI、Anthropic、Google……）维护的、配了成百上千张顶级 GPU 的集群。这些公司把模型"养"在那里，然后对外提供**模型 API**——任何应用，只要通过网络请求这个 API，就能"借用"它的理解和生成能力。

> **断点：模型远在云端，CoinJar 想用它，必须跨越网络去"调用"它——就像第八部调用远端服务器、第十三部调用支付平台一样。**

而你马上会发现，这次调用的骨架，和第八、十三部学的那套，**原封不动**。

## 15.2　比喻：请一位住在云端的"语言专家"远程坐诊

想象你是一位乡村医生，遇到一个疑难病例，自己拿不准。

你不可能把病人扛到城里的大医院，也不可能把那位顶尖专家请到你的诊所常驻（太贵了）。

你能做的是：**打个电话**，把病情描述给专家听，专家远程给你诊断意见，然后你根据意见给病人开药。

这正是 CoinJar 和模型的关系：

> - **CoinJar**（应用）= 乡村医生：有具体的病人（用户的话），但自己不懂诊断（不会理解语言）。
> - **模型**（远端 AI）= 顶尖专家：住在大医院（云端），有极强的诊断能力（理解语言），但不亲自来你这儿。
> - **模型 API**（网络接口）= 那个电话线：你通过它，把病情（用户的话）发过去，专家通过它，把诊断（理解后的结果）发回来。

专家不知道病人的家庭情况、不会亲自开药、不碰病人的病历——他只负责"理解病情、给建议"。**真正执行**（开药、写病历）的，还是你。

同样，模型不知道你的数据库在哪、不会自己去写数据、不碰你的服务器——它只负责"理解用户的话、给结构化的建议"。**真正执行**（写数据库）的，还是 CoinJar 的代码。

这个分工，贯穿卷三剩下的所有部分。牢牢记住：**模型是个远程的"语言专家"，它只懂语言，不动手。**

## 15.3　模型 API：向一个 AI 大脑"提要求"

现在正式化这个"打电话"。

模型 API，就是模型提供方（如 OpenAI）开放给外界的**网络接口**，让你的程序能通过网络请求，调用模型的能力。

这个 API 的用法，和第八部学的那套"客户端—服务器"、第十三部学的"调用第三方服务"，**骨架完全一致**：

```
第八部（调用服务器）：
  客户端发起 HTTP 请求 → 服务器处理 → 返回响应

第十三部（调用支付平台）：
  CoinJar 后端发起请求 → 支付平台处理付款 → 返回结果

第十五部（调用模型）：
  CoinJar 后端发起请求（附上用户的话） → 模型"理解+生成" → 返回回答
```

以 OpenAI 的 API 为例，一次最简单的调用大概长这样（示意，语法简化）：

```python
# CoinJar 后端代码
import 模型API库

用户的话 = "午饭花了18"

# 调用远端模型（通过网络请求）
回答 = 模型API库.调用模型(
    提示词 = 用户的话,
    模型名称 = "gpt-4",          # 指定用哪个模型
    API密钥 = "你的密钥"          # 证明你有权调用（第十三部的密钥思想）
)

打印(回答.内容)
# → 模型生成的回答："这是一笔餐饮支出，金额18元，类目是午饭。"
```

请你认出这里面全部是学过的东西：

- **网络请求**（第八部）：这个 `调用模型()` 背后，是一个 HTTP POST 请求，飞向 OpenAI 的服务器。
- **API 密钥**（第十三部）：和支付平台一样，你得先注册、拿到密钥，证明"这请求是你发的、你有权用模型"。
- **请求—响应**（第八部）：你发请求（附上提示词），模型处理（理解+生成），返回响应（生成的文字）。
- **调用外部服务**（第十三部）：你不知道、也不必知道，模型内部怎么运转、部署在哪个机房、用了多少 GPU——你只管"发请求、等结果"。API 把复杂性隔离了。

**骨架，原封不动。** "调用"这个思想，又一次在更高的尺度上重演——这次调用的，是一个**会理解语言的 AI 大脑**。而连接它的方式，仍然是第八部那套"通过网络请求提要求"。

## 15.4　一次模型调用的完整旅程：从一句话到一段回答

把一次完整的模型调用拆开，看每个环节：

```
1. 用户在 CoinJar 网页/App 输入："午饭花了18"
     ↓  （前端把这句话发给后端，第十一部的请求）
2. CoinJar 后端收到用户的话
     ↓  （后端把它包装成"提示词"，调用模型 API）
3. 后端向模型 API 发起 HTTP 请求：
     POST https://api.openai.com/v1/chat/completions
     请求体: {
       "model": "gpt-4",
       "messages": [{"role": "user", "content": "午饭花了18"}],
       "api_key": "你的密钥"
     }
     ↓  （请求通过互联网，到达 OpenAI 的服务器，第七部的网络）
4. OpenAI 的服务器收到请求：
     - 验证密钥（第十三部，证明你有权调用）
     - 把提示词交给模型（那个几百GB的语言大脑）
     - 模型"理解"提示词，"生成"回答（第十四部，生成而非查找）
     ↓  （生成完毕，返回响应）
5. OpenAI 服务器返回 HTTP 响应：
     {
       "choices": [{
         "message": {
           "content": "这是一笔餐饮支出，金额18元，类目是午饭。"
         }
       }]
     }
     ↓  （响应通过互联网，回到 CoinJar 后端）
6. CoinJar 后端收到回答
     ↓  （后端解析这段话，提取出"金额18、类目午饭"）
7. 后端调用自己的 记账() 函数，写入数据库（第九部）
     ↓
8. 后端把结果发给前端，前端刷新界面（第十一部）
```

这条链，串起了卷一、卷二、卷三的几乎所有连接。而你会发现，**步骤 3→4→5，正是第八部"客户端请求—服务器响应"那套，原封不动地复用了。** 只不过这次的"服务器"是个 AI 公司的集群，这次的"处理"是模型的理解和生成。

请你特别注意 CoinJar 在这条链里的角色：

> CoinJar 对模型来说，是个**客户端**（发请求的一方）。
> 模型对 CoinJar 来说，是个**服务器**（提供能力的一方）。
>
> 第八部那个"客户端—服务器"的角色划分，又一次出现了。而这次，服务器提供的不是数据、不是网页，而是**理解和生成语言的能力**。

## 15.5　提示词工程：怎么"问"，决定了怎么"答"

现在讲一个极其重要、且极具实践价值的话题——**提示词工程**（Prompt Engineering）。

第十四部说：提示词是你对模型说的话，是这次"调用"的"参数"。可"怎么说这句话"，大有讲究。

问题在于：**模型虽然强大，但它"理解"你的话时，高度依赖你怎么说。** 同样一件事，说法不同，模型的回答质量可能天差地别。

举例：

**糟糕的提示词**：
```
用户："午饭花了18"
模型回答："好的！"  （它只是礼貌回应，没提取出任何结构化信息）
```

**改进的提示词**：
```
你（在代码里构造的提示词）：
  "用户说了一句话：'午饭花了18'。
   请判断：这是否是一次记账操作？如果是，请提取出：金额、类目。
   以 JSON 格式返回。"

模型回答：
  {
    "是记账": true,
    "金额": 18,
    "类目": "午饭"
  }
```

看到区别了吗？**你给模型的"任务"越明确、格式要求越清晰，它的回答就越可用。**

这就是提示词工程的核心：**把你的需求，清清楚楚、毫不含糊地告诉模型；把你要的输出格式，具体到它无需猜测。**

几个实战技巧（这些技巧，开发者天天在用）：

**① 明确角色和任务**
```
"你是一个记账助手。用户会说一句话，你的任务是判断这是否是记账操作，
 并提取金额和类目。"
```

**② 给示例（few-shot）**
```
"用户说：'午饭花了18' → 金额:18, 类目:午饭
 用户说：'打车回家50' → 金额:50, 类目:交通
 现在用户说：'看电影花了80' → ?"
```
（模型看到示例，会更准确地模仿你要的格式）

**③ 要求特定格式（如 JSON）**
```
"请以 JSON 格式返回，格式：{金额: 数字, 类目: 字符串}"
```
（这样你的代码才好解析）

**④ 加约束和边界**
```
"如果用户的话不是记账操作，返回 {是记账: false}。
 不要编造任何用户没说的信息。"
```
（防止模型"脑补"出不存在的东西，第十四部的"幻觉"）

提示词工程，本质上是**在用自然语言"编程"**——你不是在写 Python、写 Java，而是在用人话，告诉模型"你要什么"。而这种"编程"，有它自己的规律和技巧。

> **从第二部"模块接口"到第十五部"提示词工程"的对比：**
> - 模块接口：你要**精确地写**函数签名、参数类型，不容半点歧义。
> - 提示词：你要**清晰地说**你要什么、什么格式，但用的是自然语言，容忍一定模糊。
>
> 接口思想的又一次放大——只不过这次接口是"用人话描述的"。

## 15.6　上下文：模型怎么"记住"刚才说过的话

一个多轮对话的场景：

```
用户："午饭花了18"
CoinJar（调用模型）→ 模型回答："好的，记一笔午饭18元。"

用户："刚才那笔改成20"
CoinJar（再次调用模型）→ 模型回答："？？？哪笔？"
```

问题来了：**模型怎么不记得"刚才那笔"是哪笔？**

答案是：**模型本身不记事。** 每次调用模型 API，对模型来说都是**全新的、独立的一次**。它不会"记住"上一次你说了什么——除非你**主动告诉它**。

怎么告诉？把之前的对话，**全部附在这次的请求里**。这叫**上下文**（context）。

```python
# 第一次调用
历史对话 = []
历史对话.追加({"角色": "用户", "内容": "午饭花了18"})

回答1 = 模型API.调用(消息=历史对话)
历史对话.追加({"角色": "助手", "内容": 回答1})

# 第二次调用
历史对话.追加({"角色": "用户", "内容": "刚才那笔改成20"})

回答2 = 模型API.调用(消息=历史对话)
# ↑ 这次请求里，附上了完整的历史：
#   [用户:"午饭花了18", 助手:"...", 用户:"刚才那笔改成20"]
# 模型看到"刚才那笔"时，能从前面的对话里找到指代
```

**上下文，就是你每次请求时，附上的"到目前为止所有对话"的列表。** 模型读到这个列表，才知道"刚才说了什么"，才能理解"刚才那笔"指的是哪笔。

这和第十二部的**会话**（session）思想很像：

> 第十二部：服务器要"记住"用户登录了，靠的是**令牌**——每次请求带上令牌，服务器就知道"你是之前登录的那个人"。
>
> 第十五部：模型要"记住"刚才聊了什么，靠的是**上下文**——每次请求带上历史对话，模型就知道"之前说过什么"。
>
> 都是"无状态的服务"靠**客户端主动回传信息**来"恢复状态"的思想。

但有个代价：**上下文越长，请求越慢、越贵。** 因为模型要"读"完整个上下文才能回答，对话越长，模型要处理的文字越多，费时费钱。所以实践中，当对话太长时，会做**上下文压缩**——只保留最近几轮，或者把前面的对话总结一下再传。

## 15.7　不确定性：同一句话，模型可能答得不完全一样

回到第十四部留下的那个重要警告：**模型有不确定性**。

同样的提示词，调用两次，模型的回答**可能措辞不同、甚至侧重点不同**。

```
提示词："午饭花了18，提取金额和类目"

第一次回答：{"金额": 18, "类目": "午饭"}
第二次回答：{"金额": 18, "类目": "餐饮"}  （类目词换了）
```

为什么？因为模型是**生成式**的（14.6 节）——它每次生成时，是在"从符合语言规律的若干可能答案里，挑一个概率高的"。而"午饭"和"餐饮"都合理，它可能这次挑这个、下次挑那个。

这对使用者意味着什么？

**① 不要依赖模型"永远回答一模一样"**——它不像数据库查询，不是确定的。

**② 关键操作要加验证**——如果模型说"金额是 18"，你最好再检查一遍这个数字是不是合法、是不是用户真的说了这个数（尤其当金额涉及钱）。

**③ 可以调节"温度"参数**——模型 API 通常有个参数叫 `temperature`（温度），调低它（如 0.2），模型会更"保守"、回答更确定；调高它（如 0.8），模型更"发散"、更有创意。记账这种事，要低温度（稳定）；写创意文案，可以高温度（多样）。

**不确定性是模型的天性，不是 bug。** 它带来灵活和创造力，代价是你不能像信任数据库一样信任它。这就是为什么后面几部，我们会不断强调"模型只负责理解，真正执行要加防护"（第十六部）和"关键数据要从你的数据库取、不能让模型凭空生成"（第十七部）。

## 15.8　成本与延迟：模型调用，比普通函数贵得多、慢得多

最后讲两个你必须清醒认识的现实代价——**钱**和**时间**。

**成本**：调用模型 API，**按字数收费**。

- 你发给模型的文字（提示词）要算钱（"输入 token"）；
- 模型生成的文字（回答）也算钱（"输出 token"，通常更贵）。
- 一次调用，少则几美分，多则几美元（如果上下文很长、生成很长）。

对比：

> 调用你自己的函数（第一部）：不花钱，几微秒。
> 查数据库（第九部）：几乎不花钱，几毫秒。
> 调用模型（第十五部）：花钱，几秒。

所以，**不是所有事都该调模型**。能用函数解决的，别调模型；能查数据库的，别调模型。模型应该用在"只有它能干的事"——理解自然语言、生成语言、做语义判断。

**延迟**：一次模型调用，**通常要几秒**。

- 网络往返（CoinJar 后端 ↔ OpenAI 服务器）要时间；
- 模型生成文字（一个字一个字"写"出来）要时间。

这比第一部的函数（几微秒）、第九部的数据库查询（几毫秒）、甚至第八部的普通网络请求（几百毫秒），都慢得多。

所以，**用户体验上要做好"等待"的准备**：

- 显示"思考中…"的提示；
- 或者用"流式返回"（模型生成一个字就传回一个字，让用户边等边看，像打字机一样），体验会好很多。

成本和延迟，是 AI 时代的新约束。它们决定了你不能无节制地调模型——要像个精打细算的管家，只在真正需要"理解语言"的地方用它。

## 15.9　回到 CoinJar：后端接入模型 API，把用户的话变成结构化账目

把这一部的全部，落到 CoinJar 后端的一段完整代码上。

```python
# CoinJar 后端：接入模型 API，处理用户的自然语言记账

import 模型API库
模型API密钥 = 读取环境变量("模型API密钥")  # 保密！藏在后端（第十三部）

@服务器.路由("POST /AI记账")
函数 AI记账(请求):
    用户ID = 检查身份(请求)                   # 第十二部：先确认你是谁
    用户的话 = 请求.body.用户输入
    
    # —— ① 构造提示词（提示词工程，15.5） ——
    提示词 = f"""
你是记账助手。用户说了一句话："{用户的话}"。
请判断：这是否是一次记账操作？
如果是，请提取：金额（数字）、类目（字符串）、日期（默认今天）。
以 JSON 格式返回：{{"是记账": true/false, "金额": ..., "类目": ..., "日期": ...}}
不要编造用户没说的信息。
"""
    
    # —— ② 调用模型 API（网络请求，15.3） ——
    回答 = 模型API库.调用模型(
        模型名称 = "gpt-4",
        提示词 = 提示词,
        API密钥 = 模型API密钥,
        温度 = 0.2                            # 低温度，要稳定（15.7）
    )
    
    # —— ③ 解析模型的回答（从 JSON 字符串变成数据） ——
    解析结果 = JSON.解析(回答.内容)
    
    if 解析结果["是记账"]:
        金额 = 解析结果["金额"]
        类目 = 解析结果["类目"]
        日期 = 解析结果["日期"] or 今天()
        
        # —— ④ 验证（不盲信模型，15.7） ——
        if 金额 <= 0 or 金额 > 1000000:
            返回响应({"错误": "金额不合理"}, 状态码=400)
        
        # —— ⑤ 真正执行：写数据库（第九部） ——
        数据库.执行("INSERT INTO 账目表 (用户ID, 金额, 类目, 日期) VALUES (?,?,?,?)",
                   [用户ID, 金额, 类目, 日期])
        
        # —— ⑥ 返回给前端 ——
        返回响应({
            "成功": true,
            "账目": {"金额": 金额, "类目": 类目, "日期": 日期},
            "AI回复": f"已记录：{类目} {金额} 元"
        }, 状态码=200)
    else:
        返回响应({"AI回复": "我没听懂你是要记账，能再说清楚一点吗？"}, 状态码=200)
```

一次完整的"用户说人话 → AI 理解 → 真正记账"流程：

```
用户在前端输入："午饭花了18"
  → 前端发请求给后端（第十一部）
  → 后端构造提示词（15.5），调用模型 API（15.3，网络请求）
  → 模型理解、生成 JSON（第十四部）
  → 后端解析 JSON，提取金额/类目
  → 后端验证数据合理性（15.7，不盲信）
  → 后端调用数据库，真正写入（第九部）
  → 后端返回结果给前端
  → 前端刷新界面，用户看到"已记录：午饭 18 元"
```

**CoinJar 至此，真正听懂了人话、能自动记账了。** 李姐再也不用学那五步操作，她只要说一句"午饭花了18"。

## 15.10　断点预告：模型能"听懂"，可它自己动不了手

这一部，CoinJar 接通了模型，能把用户的话"翻译"成结构化信息。但请你注意代码里一个微妙的分工：

> **模型只负责"理解"用户的话、提取信息**（步骤 ②③）；
> **真正"执行"（写数据库），还是 CoinJar 自己的代码在干**（步骤 ⑤）。

模型生成了一个 JSON：`{金额:18, 类目:"午饭"}`，但它**没法自己调用 `数据库.执行()`**——因为它只是个远端的"语言大脑"，不知道你的数据库在哪、怎么连、也不知道你的函数叫什么。

目前，是 CoinJar 的代码**手动**把模型的输出，翻译成了函数调用。这种"手动翻译"，当任务简单时（记一笔账）还行，可一旦任务复杂——

> 用户说："查一下这个月外卖花了多少，如果超过 1000 就提醒我"
>
> 这需要：
> 1. 调用 `数据库.查询()` 查外卖
> 2. 算总和
> 3. 和 1000 比较
> 4. 如果超了，调用 `发提醒()`

模型能**理解**这个复杂意图、能**规划**出这几个步骤，但它**不会动手执行**。而你不可能在代码里把所有可能的复杂任务都预先写死"手动翻译"——那又回到了"无数个按钮"的老路。

> **断点：模型能听懂、能规划，可它不知道你的函数、调不了你的数据库。怎么让模型能够"指挥"你的代码、调用你的函数？**

这就是"角色反转"的那一刻——**从"人调用函数"，到"AI 调用函数"**。

> **下一站，第十六部：模型与工具。**
> 我们将看到，怎么把你的函数"描述"给模型，让模型决定"该调哪个函数、传什么参数"——这就是 **Function Calling（工具调用）**，AI 时代最激动人心的连接之一。
